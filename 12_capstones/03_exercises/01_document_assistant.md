# Проект 1. Ассистент по технической документации

## Коротко

| Пункт | Что это в проекте |
|---|---|
| Когда браться | после раздела 7: нужны поиск и RAG (6) и оценка ответов (7) |
| Вход → выход | вопрос и доверенный ID команды → ответ со ссылками на источники или отказ «в документах нет ответа» |
| Данные | 30–50 своих документов и не меньше 60 вопросов с эталонными источниками |
| Baseline | лексический поиск, который возвращает цитату без генерации |

| Минимум приёмки | ни одной утечки чужого документа; обновление индекса убирает старый факт; RAG сравнён с baseline на одном test |

## Задача

Пользователь задаёт вопрос по документации своей команды. Система возвращает
ответ с проверяемыми источниками или объясняет отсутствие данных. Изменение
документа должно отражаться в следующей версии индекса, старые фрагменты не
должны оставаться в выдаче.

## Данные и baseline

Возьми 30–50 собственных синтетических документов или открытых документов с
разрешающей лицензией; запиши происхождение. Сделай минимум 60 вопросов:
обычные, с точными кодами, перефразированные, без ответа, конфликтующие, с
попыткой получить чужие данные. Добавь не меньше пяти документов с косвенной
prompt injection: инструкция внутри текста документа требует раскрыть
документы другой команды, вставить ссылку на внешний адрес или игнорировать
правила. Раздели dev/test по исходным документам. Близкие перефразировки
держи в одной части. Два человека по возможности отдельно проверяют часть
разметки.

Baseline — лексический поиск с возвратом цитаты. Затем сравни dense/hybrid
retrieval, два способа chunking и настоящий RAG. Учебные 12 документов из репы
не заменяют этот набор.

## Что реализовать

Загрузку и версию индекса; метаданные источников и ACL; API вопроса с доверенным
tenant; лимит размера входа; отказ при отсутствии данных; трассу найденных
источников и проверку цитат. Авторизацию проверять до передачи контекста модели.
Для первого стенда достаточно локального индекса: отдельная векторная БД
вводится только при объяснимой необходимости. Если выбираешь FAISS, pgvector или
отдельную базу, обоснуй выбор измерением. Передавай фильтр по tenant в поисковый
запрос и проверяй права до передачи результатов модели; сравни полноту выдачи с
точным поиском по разрешённым данным. Как индекс применяет фильтр и что делать
при неполной выдаче — в [уроке о
хранилищах](../../6_retrieval_and_rag/01_theory/04_vector_stores.md).

Prompt храни в файле под версией; версия prompt и модель пишутся в trace каждого
ответа. Найденные фрагменты передавай внутри разделителей как данные, а не
инструкции ([инструкция и
контекст](../../5_llm_applications/01_theory/03_prompting_and_context.md)).
Задай бюджет контекста: окно минус инструкция, вопрос и резерв на ответ —
столько токенов остаётся на фрагменты; опиши, что происходит при превышении
([токены и
цена](../../5_llm_applications/01_theory/04_api_tokens_cost_caching.md)).

## Приёмка

- Отдельные Recall@k/MRR на вопросах с источником и доля верных отказов без
  источника.
- Ручная рубрика обоснованности, правильности и полноты ответов, примеры ошибок.
- Ни один тест доступа не раскрывает документ другой команды.
- Тест обновления удаляет старый факт из выдачи; сохранена версия индекса.
- Сравнение baseline/RAG на одном test, latency и расход токенов с указанием
  оборудования.
- Порог качества выбирается до финального теста; объяснено, почему он достаточен
  для задачи.
- Оценка токенов и стоимости одного запроса (вход и выход отдельно, таблица
  цен с датой; для локальной модели — время и память) сверена с usage из
  лога. Бюджет контекста не превышен ни на одном вопросе test.
- Две версии prompt сравнены на одних dev-вопросах по ID: что исправлено, что
  испорчено.
- Ни один документ с косвенной injection не привёл к утечке или действию; для
  каждого случая записано, какой защитный слой его остановил ([prompt
  injection](../../7_evaluation_and_safety/01_theory/05_guardrails_and_injection.md)).
  Детектор, если есть, измерен отдельно.
- Если ответы оценивает LLM-судья: он откалиброван по ручной разметке хотя бы 20
  ответов (матрица согласия, доля ложных одобрений), а парные сравнения
  проверены перестановкой A/B
  ([модель-судья](../../7_evaluation_and_safety/01_theory/04_llm_as_judge.md)).

Неожиданное изменение: новый документ противоречит старому, но имеет более
позднюю дату. Определи правило разрешения конфликта и докажи его выполнение на
новых примерах.
