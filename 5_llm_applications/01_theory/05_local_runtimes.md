# Как запустить модель на своём компьютере

Служба безопасности запретила отправлять текст обращений внешнему
провайдеру: в них бывают имена клиентов и адреса серверов. Значит, модель
нужно запустить у себя. В интернете десяток вариантов: Transformers,
llama.cpp, Ollama, LM Studio, vLLM, — и у каждой модели по несколько файлов
с пометками Q4, Q8, FP16. Что из этого выбрать и поместится ли модель в
память?

В [уроке 04](04_api_tokens_cost_caching.md) мы считали деньги за токены
хостингового API. Локальный запуск меняет плату за токены на плату за
железо и обслуживание. Пример `01_generate.py` из этого раздела уже
запускает модель локально через Transformers — с этого и начнём. Ни одна
команда в этом уроке не выполняется в курсе: они показаны текстом, чтобы
узнавать их в документации.

## Из чего состоит локальный запуск

Чтобы модель ответила, нужны четыре вещи:

1. **Веса** — файл или набор файлов с числами модели.
2. **Токенизатор и chat template** — как превратить сообщения с ролями в
   токены (урок 01). Неверный шаблон даёт бессмысленные ответы даже у
   хорошей модели.
3. **Движок** — программа, которая выполняет вычисления на CPU или GPU.
4. **Интерфейс** — вызов функции в Python или HTTP-сервер, к которому
   обращается приложение.

Инструменты ниже различаются тем, какие из этих частей берут на себя.

## Пять инструментов

**Transformers** — библиотека Python от Hugging Face, которой пользуется
курс. Загружает веса в формате safetensors, даёт полный доступ к модели:
можно посмотреть logits, обучить адаптер (раздел 8), поменять генерацию.
Цена гибкости — скорость: на CPU большие модели работают медленно, а
HTTP-сервер придётся написать самому (раздел 10). Хороший выбор для учёбы
и экспериментов.

**llama.cpp** — движок на C/C++, оптимизированный в том числе для обычных
CPU. Работает с файлами **GGUF** — одним файлом, где лежат квантованные
веса и сведения о токенизаторе (подробно о формате — в [разделе
10](../../10_serving_and_operations/01_theory/02_inference_optimizations.md)).
Есть консольная программа и встроенный HTTP-сервер:

```text
llama-server -m ./models/model-q4_k_m.gguf --port 8080
```

**Ollama** — обёртка для удобства: сама скачивает модели из своего
каталога, хранит их и держит локальный сервер (по умолчанию порт 11434).
Внутри использует GGUF-модели и движок на основе llama.cpp. Две команды —
и модель отвечает:

```text
ollama pull <модель>
ollama run <модель>
```

**LM Studio** — настольное приложение с окном: поиск и загрузка моделей,
чат, переключатель «запустить локальный сервер» (по умолчанию порт 1234).
Удобно, чтобы быстро попробовать модель без командной строки.

**vLLM** — серверный движок, рассчитанный в первую очередь на GPU и на
много одновременных пользователей. Экономит память KV cache и объединяет
запросы в batch; его устройство — домашняя тема [раздела
10](../../10_serving_and_operations/01_theory/02_inference_optimizations.md).
Запуск сервера выглядит так:

```text
vllm serve <модель> --port 8000
```

| Инструмент | Формат весов | Для чего | Интерфейс |
|---|---|---|---|
| Transformers | safetensors | учёба, исследование, обучение | Python |
| llama.cpp | GGUF | CPU, ноутбук, встраивание | CLI, HTTP |
| Ollama | GGUF | быстро запустить сервер | CLI, HTTP |
| LM Studio | GGUF и др. | попробовать в окне | GUI, HTTP |
| vLLM | safetensors и др. | GPU-сервер, много запросов | HTTP |

Набор возможностей у всех меняется от версии к версии; таблица — ориентир,
а не сравнение по документации конкретной версии.

## Поместится ли модель: считаем вручную

Квантизация — хранение каждого веса меньшим числом битов (с нуля
разобрана в [уроке о QLoRA](../../8_fine_tuning/01_theory/04_qlora.md),
здесь нужна только арифметика). Память под веса оценивается так:

```text
память весов ≈ число параметров × байтов на вес
```

FP16 — 2 байта на вес, Q8 — около 1 байта, Q4 — около половины байта.
Для модели на 7 млрд параметров:

- FP16: `7 000 000 000 × 2 = 14 000 000 000` байтов, 14 GB;
- Q8: `7 × 10⁹ × 1` = 7 GB;
- Q4: `7 × 10⁹ × 0.5` = 3.5 GB.

Реальный файл немного больше: квантизация хранит масштабы для блоков
весов, поэтому популярные варианты Q4 в GGUF занимают на практике около
4.5–5 бит на вес. К весам добавляются KV cache, который растёт с длиной
контекста, и память самой программы ([раздел
10](../../10_serving_and_operations/01_theory/01_serving_basics.md)).
Так что 7B в Q4 на ноутбуке с 16 GB RAM — реально, в FP16 — уже впритык,
а 70B в FP16 (140 GB) не поместится ни в 16, ни в 64 GB.

Почему квантованная модель ещё и быстрее? Чтобы выдать один токен, движок
читает из памяти все веса. Пусть память передаёт условные 50 GB в секунду.
Тогда для 7B в FP16 потолок — `50 / 14 ≈ 3.6` токена в секунду, в Q4 —
`50 / 3.5 ≈ 14`. Это верхняя граница, а не обещание: реальную скорость
даёт только замер.

Цена — точность. Q8 обычно почти не отличается от исходной модели, Q4
заметнее портит ответы на части задач, а ниже четырёх битов потери растут
быстрее. Насколько — проверяют на своём dev-наборе, а не по чужой
таблице.

## Посчитаем таблицу кодом

```python
# Байтов на вес: номинально, без служебных данных квантизации.
BYTES_PER_WEIGHT = {'FP16': 2.0, 'Q8': 1.0, 'Q4': 0.5}
MODELS = {'SmolLM2-135M': 135e6, '7B': 7e9, '70B': 70e9}

print(f'{"модель":>13}' + ''.join(f'{f:>9}' for f in BYTES_PER_WEIGHT))
for name, params in MODELS.items():
    # params × байты → байты; делим на 10**9, чтобы получить GB.
    row = [params * b / 1e9 for b in BYTES_PER_WEIGHT.values()]
    print(f'{name:>13}' + ''.join(f'{gb:>8.2f}G' for gb in row))
```

Вывод (`.venv/bin/python`, сеть и модель не нужны):

```text
       модель     FP16       Q8       Q4
 SmolLM2-135M    0.27G    0.14G    0.07G
           7B   14.00G    7.00G    3.50G
          70B  140.00G   70.00G   35.00G
```

Модель курса SmolLM2-135M в FP16 занимает около 0.27 GB, поэтому её и
выбрали: она запускается на любом компьютере. Строки для 7B совпадают с
ручным расчётом.

## Один формат запроса для всех: OpenAI-совместимый API

llama.cpp, Ollama, LM Studio и vLLM умеют принимать запросы в том же виде,
что и API OpenAI: `POST /v1/chat/completions` со списком сообщений. Это
называют **OpenAI-совместимым endpoint**. Приложению достаточно поменять
адрес сервера и название модели — код остаётся прежним. Запрос к локальному
серверу llama.cpp:

```text
POST http://localhost:8080/v1/chat/completions
Content-Type: application/json

{
  "model": "local",
  "messages": [
    {"role": "system", "content": "Определи команду для обращения..."},
    {"role": "user", "content": "t7: <ticket>Забыл пароль</ticket>"}
  ],
  "max_tokens": 64,
  "temperature": 0
}
```

Ответ приходит в той же форме, что в [уроке 04](04_api_tokens_cost_caching.md):
`choices[0].message.content` и `usage`. Ключ API локальному серверу обычно
не нужен, но если сервер слушает не только `localhost`, а всю сеть, без
ключа к нему подключится кто угодно.

«Совместимый» не значит «одинаковый». Сервер может не поддерживать часть
полей — structured output, вызов инструментов, `seed`, — и молча их
проигнорировать. Chat template применяет сервер, и если в GGUF-файле он
записан неверно, ответы испортятся без ошибки. Каждую новую пару «сервер +
модель» проверяй на своих dev-примерах.

## Когда локально, а когда через API

Локальный запуск выигрывает, когда:

- данные нельзя передавать наружу (как в нашей истории);
- нужна работа без интернета;
- поток запросов большой и ровный — железо окупается;
- нужна неизменность: зафиксированные веса не обновятся и не исчезнут без
  твоего решения, а модель провайдера могут заменить или вывести из
  обращения.

API выигрывает, когда:

- нужно качество самых больших моделей, которые не помещаются в твоё
  железо;
- нагрузка редкая или скачками — платишь только за использованные токены;
- нет людей, готовых обслуживать серверы, обновлять драйверы и следить за
  памятью;
- нужны услуги провайдера: кэш, batch API, structured output.

Часто выбирают оба: локальная модель для чувствительных данных и простых
задач, API — для остального. Сравнивают их на одном dev-наборе, как в
[разделе 7](../../7_evaluation_and_safety/01_theory/02_comparing_versions.md).

## Типичная ошибка

Сравнить локальную 7B в Q4 с большой моделью провайдера на трёх вопросах
и сделать вывод «локально не работает» — или наоборот. Разные размер,
квантизация и шаблон чата дают разное качество; сравнивать нужно на одном
наборе и с одинаковым prompt. Вторая ловушка — окно контекста: некоторые
программы по умолчанию выставляют окно меньше, чем поддерживает модель, и
длинный запрос обрезается без ошибки. Проверяй настройку и число входных
токенов в `usage`.

## Проверить понимание

1. Сколько памяти займут веса модели на 3 млрд параметров в FP16 и в Q4?
   Почему реальная потребность будет больше?
2. Почему Q4-версия модели обычно генерирует быстрее, чем FP16-версия той
   же модели на том же компьютере?
3. Приложение работало с API провайдера, его перевели на Ollama, поменяв
   только адрес. Что может сломаться, хотя формат запроса тот же?
4. Команде нужно обслуживать сто одновременных пользователей на сервере с
   GPU. Почему LM Studio здесь хуже подходит, чем vLLM?

<details>
<summary>Разбор вопроса 1</summary>

FP16: `3 × 10⁹ × 2 = 6 × 10⁹` байтов, 6 GB. Q4: `3 × 10⁹ × 0.5`, около
1.5 GB, на практике ближе к 1.7–1.9 GB из-за масштабов блоков. Сверх
весов нужны KV cache, который растёт с длиной контекста и числом
одновременных запросов, и память самой программы.

</details>

<details>
<summary>Разбор вопроса 2</summary>

Для каждого нового токена движок читает из памяти все веса, и на многих
устройствах скорость упирается именно в чтение памяти. Q4-файл примерно
вчетверо меньше FP16, поэтому за то же время его можно прочитать больше
раз. Точный выигрыш зависит от устройства и движка и проверяется замером.

</details>

<details>
<summary>Разбор вопроса 3</summary>

Другая модель — другое качество: результаты нужно заново проверить на
dev-наборе. Сервер может проигнорировать неподдерживаемые поля (например,
structured output), и JSON начнёт ломаться. Окно контекста по умолчанию
может оказаться меньше, и длинные запросы обрежутся. Неверный chat
template в файле модели испортит ответы без ошибки.

</details>

<details>
<summary>Разбор вопроса 4</summary>

LM Studio — настольное приложение для одного человека: удобно попробовать
модель, но оно не рассчитано на много одновременных запросов. vLLM
специально сделан для этого: экономно распределяет память KV cache и
объединяет запросы в batch, поэтому на том же GPU обслуживает больше
пользователей.

</details>
