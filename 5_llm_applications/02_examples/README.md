# Примеры и эксперименты

Команды выполняются из корня репозитория после установки зависимостей.
`02_schema.py` и `03_retry_budget.py` — профиль **CPU**: без весов, сети и
настоящих ожиданий, их можно запускать сразу. `01_generate.py` — профиль
**MODEL**: ему нужны локальные веса. Перед изменением кода сначала запиши
своё предсказание, затем меняй одно условие.

Порядок: `02_schema.py` после урока 1, `03_retry_budget.py` после урока 2,
`01_generate.py` — когда подготовишь веса (номер 01 у него потому, что он
открывает тему, а не потому, что запускается первым).

## 01_generate.py

**После урока:** [как превратить ответ модели в
результат](../01_theory/01_structured_output.md); в [уроке о локальном
запуске](../01_theory/05_local_runtimes.md) он служит примером
Transformers.

**Идея.** Настоящая генерация: список сообщений → chat template → ID
токенов → `generate` → текст ответа.

**Что нужно.** Веса SmolLM2-135M-Instruct (около 260 MiB) в
`artifacts/models/smollm2-135m/`: какие файлы и откуда скачать —
в [списке моделей](../../data/models.md). Скрипт ничего не скачивает сам
(`local_files_only=True`) и не выполняет код из папки модели
(`trust_remote_code=False`).

```bash
uv run python 5_llm_applications/02_examples/01_generate.py
```

**Без весов** скрипт печатает
`Модель отсутствует. См. data/models.md: ссылки и ручное размещение файлов.`
и завершается с кодом 1. Это сообщение о недостающем шаге, а не успешный
запуск.

**Как читать вывод с весами.** Первая строка — ответ модели на вопрос о
том, что делает индекс базы данных (по-английски: модель
преимущественно англоязычная). Вторая — `input tokens: N output tokens: M`:
сколько токенов дал chat template для одного короткого сообщения и сколько
модель сгенерировала (не больше 48, лимит `max_new_tokens`). Генерация
greedy (`do_sample=False`), поэтому на одной версии библиотек ответ
повторяется, но точный текст заранее не известен: в курсе этот пример
без весов не запускался.

**Что доказывает и чего нет.** Доказывает, что веса, токенизатор и шаблон
согласованы и модель выдаёт текст. Не доказывает, что ответ верен:
качество оценивай отдельно, на своих dev-вопросах.

**Изменение.** Замени текст в `messages` на два варианта инструкции к
одной задаче и сравни ответы. Предскажи заранее, какой вариант даст ответ
ближе к нужному формату; одного удачного ответа мало для вывода.

## 02_schema.py

**После урока:** [как превратить ответ модели в
результат](../01_theory/01_structured_output.md), раздел «Проверим ответ по
слоям».

**Идея.** Проверка формата ответа слоями: JSON → объект с нужными полями →
допустимые типы и значения.

**Входные данные.** Четыре заранее написанных ответа «модели»: один
корректный, без `ticket_id`, с категорией `invented` и вообще не JSON.
Настоящая модель не вызывается.

```bash
uv run python 5_llm_applications/02_examples/02_schema.py
```

**Как читать вывод.** `VALID {...}` — ответ прошёл все проверки. `INVALID` и
текст причины — какой слой его отверг: `Expected exactly ticket_id and label`
(поля), `Unknown label` (значение), `Expecting value: line 1 column 1` —
сообщение `json.loads` о том, что это не JSON. `try/except` в цикле нужен, чтобы
ошибка одного ответа не останавливала проверку остальных (см. [урок об
исключениях](https://github.com/krasnosvar/4_python_my_knowledgebase/blob/main/1_python/1_python_fundamentals/07_exceptions/01_theory/01_exceptions.md)).

**Что доказывает и чего нет.** Схема ловит нарушения формата. Последняя
строка вывода напоминает: `VALID` не значит «верно по смыслу».

**Изменение.** Добавь в `cases` ответ
`'{"ticket_id":"t1","label":"database"}'` для обращения «Забыл пароль».
Предскажи: он будет `VALID`, хотя категория неверна. Чтобы поймать такую
ошибку, нужен размеченный правильный ответ, а не схема.

## 03_retry_budget.py

**После урока:** [что делать, если модель не ответила
вовремя](../01_theory/02_runtime_contract.md).

**Идея.** Решение о повторе: временные ошибки (429, 5xx) повторяются с
растущей паузой, постоянные (например, 401) — нет, а число попыток
ограничено.

**Входные данные.** Заранее заданные списки HTTP-статусов, которые сервер
«вернул бы» на попытки 1, 2, 3. Это симуляция: нет ни сети, ни настоящего
ожидания, паузы только записываются в `planned_backoff_seconds`.

```bash
uv run python 5_llm_applications/02_examples/03_retry_budget.py
```

**Как читать вывод.** Для сценария `[429, 503, 200]` видно три попытки:
после первой запланирована пауза 1 секунда, после второй — 2, третья
успешна, итог `'status': 'ok'`. Три `assert` перед печатью также
проверяют, что 401 не повторяется, а десять ответов 503 дают ровно три
попытки.

**Что доказывает и чего нет.** Проверяет правила решения о повторе
отдельно от сети. Не измеряет время и не моделирует jitter, `Retry-After`
и отмену — о них напоминает последняя строка вывода.

**Изменение.** Добавь общий бюджет времени: параметр `deadline_seconds` и
остановку, когда сумма запланированных пауз его превысила бы. Предскажи,
сколько попыток останется у `[503]*10` при бюджете 2 секунды. В отчёте
объясни, почему повтор генерации текста безопаснее повтора платежа.
