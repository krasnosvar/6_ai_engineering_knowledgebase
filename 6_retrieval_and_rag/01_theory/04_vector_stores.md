# Где хранить векторы, когда документов миллион

В учебном примере поиск сравнивает вопрос с каждым из десятка фрагментов.
Представим, что фрагментов стало миллион, а запросов — сотня в секунду.
Полный перебор становится дорогим, и нужен индекс, который ищет быстрее, но
иногда ошибается. Разберём, как устроен такой поиск, как измерить его
ошибку и где хранить векторы вместе с правами доступа.

Нужны из прошлых уроков: embedding текста и косинусное сходство
([ранжирование](03_ranking.md)), метаданные и обновление индекса
([подготовка документов](02_ingestion.md)), Recall@k
([основы RAG](01_rag_basics.md)) и матричное умножение
([массивы и оси](../../1_math_and_data/01_theory/04_arrays_and_axes.md)).

## Посчитаем цену полного перебора

Пусть у нас `N` фрагментов, у каждого вектор длины `D`. Для нормированных
векторов косинус — это скалярное произведение: `D` умножений и сложений.
Чтобы найти лучшие k для одного запроса, считаем все `N` сходств:

```text
N × D = 1 000 000 × 768 = 768 000 000 умножений на один запрос
```

При 100 запросах в секунду это 76.8 млрд умножений в секунду только на
поиск. Память тоже растёт: число float32 занимает 4 байта, поэтому

```text
N × D × 4 = 1 000 000 × 768 × 4 = 3 072 000 000 байт ≈ 3 ГБ
```

Цена линейна по `N`: в десять раз больше документов — в десять раз дольше
каждый запрос. Такой **точный перебор** (brute force, flat search) остаётся
эталоном качества: он всегда находит настоящие top-k. Для тысяч и десятков
тысяч фрагментов его часто достаточно, и начинать стоит именно с него.

## Идея приближённого поиска

**ANN**, approximate nearest neighbors, — приближённый поиск ближайших
соседей. Индекс заранее упорядочивает векторы так, чтобы при запросе
сравнивать вопрос лишь с малой частью корпуса. Платим за это пропусками:
иногда настоящий сосед не попадает в просмотренную часть.

**IVF** (inverted file, «инвертированный файл») делит корпус на ячейки.
Сначала выбирают, например, 100 центров методом k-means: каждый документ
относят к ближайшему центру, центр сдвигают в среднее своих документов и
повторяют. При запросе сравнивают вопрос с центрами, берут `n_probe`
ближайших ячеек и перебирают только их документы. Больше `n_probe` — выше
полнота и больше работы.

**HNSW** (hierarchical navigable small world) строит граф: каждый вектор
связан с несколькими близкими. Поиск начинается с точки входа и жадно
переходит к соседу, который ближе к запросу, пока улучшение возможно.
Верхние уровни графа редкие и дают длинные «прыжки», нижние — плотные и
уточняют результат. Параметр ширины поиска (обычно его называют `ef`)
задаёт, сколько кандидатов держать в работе: больше — точнее и медленнее.

Общий компромисс один: **recall против скорости**. Здесь Recall@k — доля
настоящих top-k из точного перебора, которую вернул ANN. Это не то же
самое, что Recall@k по размеченным вопросам из первого урока: там сравниваем
с нужными документами, здесь — с ответом точного поиска. Разделение
показывает, виноват ли индекс или сами векторы.

## Пример вручную

Корпус 20 000 векторов, 100 ячеек примерно по 200 документов. Запрос
сравниваем со 100 центрами, затем при `n_probe=3` — примерно с 600
документами трёх ячеек. Итого около 700 сравнений вместо 20 000, в 28 раз
меньше. Если 9 из настоящих 10 соседей лежат в этих трёх ячейках,
recall@10 = 9/10 = 0.9. Десятый сосед оказался в четвёртой по близости
ячейке: он был близок к запросу, но его центр — нет.

## Измерим на игрушечном IVF

Код использует только NumPy. Сохрани его в файл, например `ann.py`, и
запусти из корня репозитория `uv run python ann.py`.

```python
import numpy as np

rng = np.random.default_rng(0)
N, D, k = 20_000, 64, 10

# Синтетический корпус: 50 «тем», вокруг каждой — облако векторов.
topics = rng.normal(size=(50, D))
docs = topics[rng.integers(0, 50, N)] + 0.5 * rng.normal(size=(N, D))
docs /= np.linalg.norm(docs, axis=1, keepdims=True)
queries = docs[rng.integers(0, N, 100)] + 0.3 * rng.normal(size=(100, D))
queries /= np.linalg.norm(queries, axis=1, keepdims=True)

def exact_topk(q):
    scores = docs @ q                      # N скалярных произведений
    return set(np.argsort(-scores)[:k])

# Учебный IVF: делим корпус на ячейки по ближайшему «центру».
n_cells = 100
centers = docs[rng.choice(N, n_cells, replace=False)]
for _ in range(5):                         # несколько шагов k-means
    cell = np.argmax(docs @ centers.T, axis=1)
    for c in range(n_cells):
        members = docs[cell == c]
        if len(members):
            centers[c] = members.mean(axis=0)
    centers /= np.linalg.norm(centers, axis=1, keepdims=True)
cell = np.argmax(docs @ centers.T, axis=1)

def ivf_topk(q, n_probe):
    near = np.argsort(-(centers @ q))[:n_probe]   # ближайшие ячейки
    ids = np.flatnonzero(np.isin(cell, near))     # только их документы
    scores = docs[ids] @ q
    return set(ids[np.argsort(-scores)[:k]]), len(ids)

for n_probe in (1, 3, 10):
    recalls, compared = [], []
    for q in queries:
        found, n = ivf_topk(q, n_probe)
        recalls.append(len(found & exact_topk(q)) / k)
        compared.append(n + n_cells)
    print(f'n_probe={n_probe:2d}  recall@{k}={np.mean(recalls):.3f}  '
          f'сравнений={np.mean(compared):7.0f} из {N}')
```

`docs @ q` — вектор из `N` сходств; `centers @ q` — сходства со 100
центрами; `np.isin(cell, near)` отмечает документы выбранных ячеек.
В «сравнения» входят и 100 сравнений с центрами. Вывод:

```text
n_probe= 1  recall@10=0.640  сравнений=    388 из 20000
n_probe= 3  recall@10=0.919  сравнений=    784 из 20000
n_probe=10  recall@10=0.990  сравнений=   2144 из 20000
```

Одна ячейка даёт ускорение примерно в 50 раз, но теряет треть соседей.
Десять ячеек возвращают 99% настоящих соседей при десятой части работы.
Данные синтетические и хорошо кластеризованы; на реальных embeddings числа
будут другими, поэтому `n_probe` (или `ef` у HNSW) подбирают измерением на
своём корпусе, а не по умолчанию.

## Библиотека, расширение или отдельная база

**FAISS** — библиотека: индекс живёт в памяти вашего процесса, вы вызываете
функции поиска из кода. В ней есть и точный перебор, и IVF, и HNSW. Сервера,
прав доступа и транзакций нет: где хранить тексты и метаданные, как
обновлять и восстанавливать индекс — решает приложение. Подходит для
экспериментов, пакетной обработки и случаев, когда индекс строится целиком.

**pgvector** — расширение PostgreSQL: вектор становится колонкой таблицы,
рядом с текстом, tenant и версией документа. Фильтр по правам — обычный
`WHERE`, обновление — обычная транзакция, резервное копирование — то же,
что у остальной базы. Без индекса запрос выполняет точный перебор;
поддерживаются индексы HNSW и IVFFlat. Хороший выбор, если Postgres уже
есть, а векторов до миллионов.

**Отдельные векторные базы** — Qdrant, Weaviate, Milvus — это сервисы,
созданные для векторного поиска: хранят векторы вместе с метаданными,
фильтруют по ним во время поиска, умеют распределять индекс по нескольким
машинам. Цена — ещё одна система, которую нужно разворачивать, обновлять,
мониторить и синхронизировать с основным хранилищем документов.

Порядок выбора обычно такой: точный перебор → pgvector или FAISS → отдельная
база, когда измерения показывают, что предыдущий шаг не справляется.

## Фильтры и права внутри поиска

Права проверяются до передачи текста модели — это правило из [основ
RAG](01_rag_basics.md). В векторном индексе появляется ловушка порядка
операций. Если сначала взять ANN top-10 по всему корпусу, а потом выкинуть
чужие документы, может не остаться ни одного своего: все 10 ближайших
принадлежали другой команде. Это та же ошибка, что «фильтрация после
top-k» в [упражнении](../03_exercises/README.md), только усиленная
приближённостью.

Поэтому фильтр по tenant и версии передают в сам поиск: хранилище должно
выбирать k лучших среди разрешённых. Проверь, как это делает выбранная
система, и тестом убедись, что при узком фильтре возвращается k разрешённых
результатов. Если команд немного и данные строго разделены, иногда проще
держать отдельный индекс на каждого tenant.

**Гибридный поиск** (слова + векторы, объединение через RRF) разобран в
[уроке о ранжировании](03_ranking.md). Для хранилища это значит одно: рядом
с векторным индексом нужен лексический (например, BM25), и оба должны
видеть одинаковый набор документов и одинаковые фильтры.

## Смена embedding-модели

Векторы разных моделей несравнимы, даже если длина одинакова
([подготовка документов](02_ingestion.md)). Значит, новая модель требует
пересчитать все фрагменты и построить новый индекс. Цена на миллион
фрагментов: миллион прогонов модели — часы или дни на CPU, плюс деньги, если
embeddings считает платный API.

Безопасная процедура: строим новый индекс рядом со старым, новые и
изменённые документы пишем в оба, сравниваем Recall@k по размеченным
вопросам, переключаем приложение и держим старый индекс для отката.
Вместе с индексом храним название и версию модели: запрос нужно кодировать
той же моделью, что и документы.

## Типичная ошибка

Команда заменила точный перебор на ANN, качество ответов упало, и стали
менять промпт. Причина была в индексе: recall@10 относительно точного поиска
оказался 0.6. Проверка простая — на выборке запросов сравнить ANN с точным
перебором. Обратная ошибка — сразу ставить отдельную базу на десять тысяч
фрагментов, которые полный перебор обрабатывает за миллисекунды.

## Проверить понимание

1. Корпус вырос с 100 тысяч до 2 миллионов фрагментов при той же
   embedding-модели. Во сколько раз выросло время точного перебора на один
   запрос и почему?
2. После перехода на HNSW Recall@5 по размеченным вопросам упал с 0.82 до
   0.70. Как понять, виноваты векторы или приближённый поиск?
3. Команда A ищет по общему индексу. ANN вернул top-10, затем код удалил
   документы команды B, и осталось 2 результата. В чём ошибка и как её
   исправить?
4. Вышла новая embedding-модель с той же длиной вектора. Почему нельзя
   кодировать ею только новые документы, оставив старые векторы?

<details>
<summary>Разбор вопроса 1</summary>

В 20 раз: точный перебор считает одно скалярное произведение на каждый
фрагмент, поэтому работа равна `N × D` и растёт линейно по `N`. Длина
вектора `D` не изменилась, значит, рост определяется только `N`.

</details>

<details>
<summary>Разбор вопроса 2</summary>

Нужно на тех же вопросах получить top-5 точным перебором по тем же векторам.
Если точный перебор даёт около 0.82, а HNSW 0.70, потери вносит индекс —
увеличь ширину поиска или смени параметры. Если и точный перебор даёт 0.70,
изменились векторы или данные, а индекс ни при чём.

</details>

<details>
<summary>Разбор вопроса 3</summary>

Фильтр применён после отбора top-k: ближайшие соседи по всему корпусу
оказались в основном чужими. Фильтр по tenant нужно передать в сам поиск,
чтобы k лучших выбирались среди разрешённых, или держать отдельный индекс
команды. Проверить тестом, что возвращается k разрешённых результатов.

</details>

<details>
<summary>Разбор вопроса 4</summary>

Координаты разных моделей обучены по-разному: близость нового вектора
запроса к старому вектору документа ничего не значит. Запрос можно
закодировать только одной моделью, поэтому все документы должны быть
в пространстве этой же модели — индекс пересчитывают целиком.

</details>
