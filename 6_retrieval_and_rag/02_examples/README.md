# Примеры и эксперименты

Команды выполняются из корня репы после установки зависимостей. Профиль
показывает, что нужно для запуска: **CPU** — только Python-библиотеки,
**MODEL** — локальные веса языковой модели, **EMBEDDING** — локальные веса
embedding-модели. Веса не скачиваются автоматически: [где взять
модели](../../data/models.md). Пока их нет, MODEL- и EMBEDDING-примеры
печатают сообщение об отсутствии и завершаются; это не успешный запуск.

Все примеры читают учебный корпус `data/documents.json`: 12 коротких
английских документов. У каждого есть `id`, `tenant` (`public`, `team-a`
или `team-b`) и текст. Вопросы с разметкой нужных документов лежат в
`data/queries.json`. Для каждого опыта сначала предскажи результат, затем
измени одно условие.

## 01_search.py — поиск по словам с правами доступа

После [урока 1](../01_theory/01_rag_basics.md). Профиль: **CPU**.

```bash
uv run python 6_retrieval_and_rag/02_examples/01_search.py
```

Что делает. Для каждого из 10 вопросов `queries.json` функция `search`
сначала оставляет документы `public` и команды вопроса, затем строит TF-IDF
по этим документам и сортирует их по косинусу с вопросом (подробнее — в
[уроке о ранжировании](../01_theory/03_ranking.md)). Документы без общих с
вопросом слов отбрасываются. Recall@3 считается так же, как в уроке: доля
нужных документов среди первых трёх.

Как читать вывод. Строка `q4 dev ['d9'] recall@3= 1.0` значит: вопрос q4
из dev-части, найден только d9, единственный нужный документ найден. Для
q8 (вопрос без ответа) печатается `unanswerable; returned= []`: ни одного
общего слова, выдача пуста. `assert` в цикле проверяет, что ни один
найденный документ не принадлежит чужой команде; если он сработает,
программа упадёт с `AssertionError`.

Что доказывает и чего нет. Права проверяются до поиска, и q4/q7 с
одинаковым текстом получают разные документы (d9 и d10). Итоговый recall
1.0 на 10 коротких вопросах, почти дословно повторяющих документы,
ничего не говорит о качестве на настоящих вопросах.

Одно изменение. В `search` поменяй `k=3` на `k=1`. Предскажи, у каких
вопросов изменится выдача, а у каких Recall. Ответ: укоротятся выдачи q1,
q3, q5, q9, но нужный документ у всех стоит первым, поэтому Recall@1
останется 1.0 (подпись `recall@3=` в `print` при этом стоит поправить).
Затем добавь в конец блока `if __name__ == '__main__':` строку
`print(search('how to undo a bad release', 'public'))` — тот же
смысл, что у d12, но без его слов. Поиск вернёт d5 и d3: у них общее с
вопросом только служебное слово `to`, а d12 не найден совсем. Это
ограничение поиска по словам, которое разбирается в уроке 3.

## 04_chunking.py — фрагменты фиксированной длины

После [урока 2](../01_theory/02_ingestion.md). Профиль: **CPU**.

```bash
uv run python 6_retrieval_and_rag/02_examples/04_chunking.py
```

Что делает. Режет 12 слов на окна по `size` слов с перекрытием `overlap`
(шаг окна `size − overlap`, как в уроке) и проверяет, попала ли фраза
`error budget is forty three minutes` (слова 5–10) целиком хотя бы в одно
окно. В уроке пример был с окном 6 и перекрытием 2; здесь три другие
настройки, чтобы показать и потерю факта, и цену перекрытия. Слова считаются
по пробелам — это не токены LLM.

Как читать вывод. Для каждой настройки печатается словарь: окна
(`chunks`), сохранился ли факт (`fact_intact`) и сколько слов попало в
индекс (`indexed_words`). Ожидаемо: `(6, 0)` и `(6, 3)` теряют факт,
`(12, 0)` сохраняет; перекрытие 3 увеличивает индекс с 12 до 18 слов.

Что доказывает и чего нет. Перекрытие само по себе не гарантирует
сохранность: окна `(6, 3)` начинаются со слов 1, 4, 7, а факт начинается со
слова 5. Это расчёт на одной фразе, а не измерение качества поиска.

Одно изменение. В списке настроек замени `(6, 3)` на `(6, 4)`. Предскажи:
шаг станет 2, окна начнутся со слов 1, 3, 5, 7 — факт сохранится, а в
индекс попадёт 24 слова, вдвое больше исходного текста. Затем найди самую
маленькую настройку без перекрытия, сохраняющую факт.

## 02_rag.py — поиск и ответ языковой модели

После [урока 1](../01_theory/01_rag_basics.md), когда подготовлены веса.
Профиль: **MODEL** (SmolLM2-135M-Instruct в
`artifacts/models/smollm2-135m/`).

```bash
uv run python 6_retrieval_and_rag/02_examples/02_rag.py
```

Без весов печатает `Модель отсутствует. См. data/models.md...` и
завершается: поиск до генерации выполняется, но ответа нет.

Что делает. Пользователь из `team-a` спрашивает про бюджет ошибок atlas.
Тот же TF-IDF-поиск по разрешённым документам выбирает два лучших, код
проверяет, что среди них нет документов `team-b`, и собирает контекст с ID
источников `[d9] ...`. Модель генерирует ответ без случайности
(`do_sample=False`), не длиннее 64 токенов.

Как читать вывод. `SOURCES` — что увидела модель, `ANSWER` — что она
написала. Сравни вручную: есть ли в ответе 43 минуты и ссылка на d9.
Маленькая модель может ошибиться; код правильность ответа не проверяет.
Неверный ответ при правильных источниках — ошибка генерации, а не поиска
(урок 1, раздел «Поиск и ответ измеряются отдельно»).

Одно изменение. Замени `tenant = 'team-a'` на `'team-b'`. Предскажи:
источником станет d10, а верным ответом — 12 минут.

## 03_dense_hybrid.py — смысловой поиск и RRF

После [урока 3](../01_theory/03_ranking.md), когда подготовлены веса.
Профиль: **EMBEDDING** (all-MiniLM-L6-v2 в `artifacts/models/minilm/`).

```bash
uv run python 6_retrieval_and_rag/02_examples/03_dense_hybrid.py
```

Без весов сообщает, что модель MiniLM отсутствует, ссылается на
`data/models.md` и завершается до любого расчёта.

Что делает. Вопрос «How can I limit repeated requests after server
throttling?» не содержит слов `HTTP`, `429` и `rate`, по которым его
нашёл бы поиск по словам. Функция `encode` строит embedding текста так же,
как в уроке: среднее по реальным токенам, затем длина 1. Далее считаются
два рейтинга — dense (косинус embeddings) и lexical (TF-IDF) — и
объединяются через RRF с константой 60.

Как читать вывод. Три строки с первыми тремя ID каждого рейтинга. Нужный
документ — d8. Лексическую часть можно проверить без весов: общие слова с
вопросом есть только у d7 (`can`) и d8 (`limit`), и TF-IDF ставит d7 выше
(0.243 против 0.212). Значит, лексический рейтинг начинается с
неправильного документа из-за служебного слова. Порядок dense-рейтинга
зависит от весов модели; без запуска мы его не утверждаем.

Что доказывает и чего нет. Один вопрос показывает механику и типичную
слабость поиска по словам, но не то, что dense или гибрид лучше в целом.
Методы сравнивают на наборе вопросов (раздел 7).

Одно изменение. Замени вопрос на `HTTP 429` и предскажи, какой рейтинг
теперь надёжнее; затем на перефразировку без общих слов с d8.
