# Примеры и эксперименты

Все три примера — профиль **CPU**: работают без готовых весов и сети, на
встроенных или синтетических данных. Команды выполняются из корня репозитория
после установки зависимостей. Перед запуском предскажи результат, после —
объясни, совпал ли он с прогнозом. Затем измени одно условие и снова сравни.

Это **расчёты на учебных данных**, а не измерение качества реальной системы:
наборы крошечные или синтетические, их числа иллюстрируют идею урока.

## 01_tickets.py — первый текстовый классификатор

- **После урока:** [от обращения к
  предсказанию](../01_theory/01_classification_basics.md); отчёт читается
  после [урока о метриках](../01_theory/03_metrics.md).
- **Идея:** цепочка «текст → TF-IDF вектор → логистическая регрессия → класс»
  в одном Pipeline; `fit` только на train, `predict` на test.
- **Данные:** [data/tickets.json](../../data/tickets.json) — 18 англоязычных
  обращений трёх классов (`database`, `network`, `access`); поле `split`
  заранее делит их на 12 train и 6 test.

```bash
uv run python 2_classical_ml/02_examples/01_tickets.py
```

**Как читать вывод.** Сначала `classification_report`: precision, recall и F1
по каждому классу, `support` — число test-примеров класса (здесь по 2). Затем
каждое test-обращение с предсказанным и правильным классом. Сейчас все 6
угаданы, отчёт показывает 1.00.

**Что доказывает:** код обучения и применения работает, TF-IDF строится только
на train. **Чего не доказывает:** что модель хороша. На 6 примерах одна ошибка
меняет recall класса на 0.5; [урок о
кросс-валидации](../01_theory/04_cross_validation.md) показывает среднюю
accuracy 0.333 на фолдах из 12 обучающих обращений.

**Python в примере.** Функция `data()` читает JSON-файл: `Path` собирает путь к
`data/` от расположения скрипта, `json.loads` превращает текст в список
словарей. Подробнее — уроки Python о
[pathlib](https://github.com/krasnosvar/4_python_my_knowledgebase/blob/main/1_python/6_standard_library/01_theory/06_pathlib_os_filesystem.md)
и
[json](https://github.com/krasnosvar/4_python_my_knowledgebase/blob/main/1_python/6_standard_library/01_theory/05_json_csv_serialization.md).
Строки `[r for r in rows if ...]` — генераторы списков
([урок](https://github.com/krasnosvar/4_python_my_knowledgebase/blob/main/1_python/1_python_fundamentals/05_collections/01_theory/03_comprehensions.md)).

**Изменение: символы вместо слов.** В строке `make_pipeline(...)` замени
`TfidfVectorizer()` на `TfidfVectorizer(analyzer='char_wb', ngram_range=(2,
4))` — признаками станут группы из 2–4 символов. Предскажи: изменится ли
отчёт? Затем добавь в `test` своё обращение с опечаткой, например `{'text':
'paswrd reset', 'label': 'access'}`, и сравни оба варианта. Различие на
нескольких текстах — повод для гипотезы, а не вывод: для честного сравнения
нужен dev, выделенный из train (это задание 3 в
[упражнениях](../03_exercises/README.md)).

## 02_leakage.py — утечка через группы

- **После урока:** [как разделить данные](../01_theory/02_model_selection.md),
  раздел об утечке.
- **Идея:** если строки одного клиента попадают и в train, и в test, оценка
  измеряет запоминание клиента, а не умение работать с новыми.
- **Данные:** синтетические, генерируются в коде: 200 клиентов по 4 строки,
  метка каждого клиента выбрана случайно (`rng.randrange(2)`). Связи между
  входом и меткой нет, угадать лучше монетки честно нельзя.

```bash
uv run python 2_classical_ml/02_examples/02_leakage.py
```

**Как читать вывод.** Две строки accuracy. При случайном разбиении строк 98%
test-строк принадлежат клиентам из train, и «модель», которая просто помнит
метку каждого ID (функция `evaluate`, словарь `lookup`), получает 1.000. При
разбиении по клиентам знакомых нет, модель отвечает частой меткой train и
получает 0.560 — уровень угадывания. `random.Random(42)` фиксирует случайность,
поэтому числа повторяются при каждом запуске; `assert` в конце проверяет, что
разрыв остался.

**Что доказывает:** способ разбиения сам по себе может создать
«идеальный» результат без какой-либо закономерности. **Чего не доказывает:**
что разбиение по группам всегда достаточно — почти одинаковые обращения с
разными ID оно не поймает.

**Изменение.** Поменяй `ROWS_PER_GROUP = 4` на `1`. Предскажи до запуска: что
станет с первой accuracy, если у каждого клиента одна строка? Проверка
`assert` в последней строке упадёт с `AssertionError` — это и есть результат
опыта: знакомых клиентов в test больше нет, и обе accuracy оказываются около
0.6, на уровне угадывания. Затем объясни, какие реальные поля (email, хост,
номер договора) могут играть роль ID.

## 03_trees.py — сложность модели и переобучение

- **После урока:** [почему сложная модель не всегда
  лучше](../01_theory/05_regularization.md).
- **Идея:** глубокое дерево запоминает train, ограниченное дерево и boosting
  обобщают лучше; линейная модель ограничена прямой границей.
- **Данные:** `make_moons` генерирует 300 точек двух переплетённых
  «полумесяцев» с шумом; 70% идут в train, 30% в validation. `random_state=42`
  делает данные и результат одинаковыми при каждом запуске.

```bash
uv run python 2_classical_ml/02_examples/03_trees.py
```

**Как читать вывод.** Для каждой модели — accuracy на train, на validation и
разрыв между ними:

```text
linear      train=0.862 validation=0.844 разрыв=+0.017
deep_tree   train=1.000 validation=0.800 разрыв=+0.200
small_tree  train=0.919 validation=0.844 разрыв=+0.075
boosting    train=0.943 validation=0.900 разрыв=+0.043
```

Большой разрыв у `deep_tree` — признак переобучения. Маленький разрыв у
`linear` при не самой высокой validation — модель стабильна, но слишком проста
для изогнутой границы. Словарь `models` хранит четыре модели под именами, цикл
обучает и оценивает каждую одинаково.

**Что доказывает:** ограничение сложности уменьшает разрыв train/validation на
этих данных. **Чего не доказывает:** что boosting всегда лучший — это одно
разбиение одного синтетического набора, и выбор по validation ещё требует
итоговой проверки на независимом test.

**Изменение.** У `small_tree` поменяй `max_depth=3` на 1, 5 и 10. Предскажи,
как будут меняться train и validation. При глубине 1 дерево задаёт один
вопрос и недообучается (train около 0.83), при 10 почти запоминает train
(около 0.995) и проигрывает на validation. Выбери глубину по validation, затем
проверь её один раз на новых данных: сгенерируй `make_moons` с другим
`random_state` и посчитай accuracy уже обученной модели.
