## 1. `binary_metrics`

**Ход мысли.** Сначала проверяем вход: пустые списки, разная длина и метки не
из `{0, 1}` — это ошибка вызова, о ней нужно сообщить сразу, а не считать
что-то по половине данных. Затем один проход по парам `(truth, pred)`
считает три клетки матрицы ошибок: TP (1 и 1), FP (0 и 1), FN (1 и 0). TN для
этих трёх метрик не нужен. Дальше формулы урока:
`precision = TP/(TP+FP)`, `recall = TP/(TP+FN)`, F1 — их гармоническое
среднее.

**Нулевой знаменатель.** `truth=[0,1]`, `pred=[0,0]`: модель не выдала ни
одной единицы, TP+FP=0, precision не определена. По условию возвращаем 0.0.
F1 тоже нужно защитить: при precision=recall=0 знаменатель
`precision+recall` равен нулю.

**Типичные ошибки:**

- перепутать FP и FN — тогда precision и recall меняются местами; проверка на
  `[1,1,0,0]`/`[1,0,1,0]` этого не заметит (там FP=FN), поэтому полезно
  вручную посчитать пример с разными FP и FN;
- `zip` без проверки длины молча обрезает длинный список — отсюда явная
  проверка `len(truth) != len(pred)`;
- считать F1 как обычное среднее `(p+r)/2`: для p=0.4, r=0.8 оно даёт 0.6
  вместо 0.533 и не наказывает за маленькую величину.

## 2. `group_overlap`

**Ход мысли.** Нужно не «сколько строк», а «какие ID встречаются в обеих
частях», поэтому переводим оба списка в множества и берём пересечение `&`.
Повторы внутри одного списка при этом исчезают автоматически.

**Ограничение.** Пустое пересечение — необходимое, но не достаточное условие
честного разбиения: почти одинаковые обращения могут прийти под разными ID, а
один клиент — под двумя учётными записями.

## 3. Письменное задание

Классификатор «всегда 0» на 99 отрицательных и одном положительном:
accuracy `99/100 = 0.99`, recall `0/1 = 0`. Для аварийных обращений он
бесполезен: единственная авария пропущена, а пропуск аварии обычно дороже
многих ложных тревог. Высокая accuracy создана только редкостью класса.

Про сравнение словесного и символьного TF-IDF: на трёх dev-обращениях каждое
означает треть accuracy, поэтому разница в одно обращение может быть
случайностью выбора dev. Вывод нужно формулировать как гипотезу для проверки
на большем наборе.

Проверки `check.py` подтверждают контракт функций на обычных и граничных
случаях. Понимание темы показывает твой отчёт и самостоятельный эксперимент.
