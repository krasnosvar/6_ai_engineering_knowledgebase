# Как выбрать модель, которая работает на новых обращениях

В [предыдущем уроке](01_classification_basics.md) мы научились представлять
обращения числами и получили несколько способов классификации. Теперь нужно
выбрать один из них. Разберём, какие данные использовать для обучения, какие —
для выбора настроек, а какие оставить для окончательной проверки. Это основа
честного эксперимента.

Представим, что сотрудники разметили 1000 обращений: для каждого известна
правильная команда. Мы хотим узнать, какой вариант программы лучше справится с
будущими запросами.

## Почему нельзя проверить только знакомые примеры

Допустим, модель после обучения правильно распределяет все 1000 обращений. Это
хороший знак для работы алгоритма обучения, но ещё не ответ на наш вопрос.
Программа могла бы просто запомнить пары «текст — команда». На знакомых
обращениях такой словарь безошибочен, а для новой формулировки готового ответа в
нём нет.

Модель обычно устроена сложнее словаря, но тоже может слишком сильно
приспособиться к знакомым примерам. Поэтому проверять её нужно на данных,
которые не участвовали в подборе весов. Способность справляться с новыми
примерами называется **обобщением**.

## Разделим обращения до начала эксперимента

Для нашего учебного примера возьмём такое разбиение:

| Часть | Обращений | Назначение |
|---|---:|---|
| Train — обучающая | 600 | Подбор весов и обучаемых преобразований |
| Validation, или dev — для выбора | 200 | Сравнение вариантов и настройка |
| Test — итоговая проверка | 200 | Оценка решения после завершения выбора |

Это пример пропорции, а не обязательное правило 60/20/20. При маленьком наборе в
каждой части может оказаться слишком мало редких случаев. При большом наборе
достаточность проверочной части определяется задачей и нужной точностью оценки.

Обучим два варианта на одних и тех же 600 обращениях. Затем дадим каждому тексты
из validation. Правильные категории используем только для сравнения с ответами
модели.

Предположим, первый вариант правильно распределил 160 обращений, второй — 180.
Доли правильных ответов равны `160/200=80%` и `180/200=90%`. Долю правильных
ответов называют **accuracy**; когда она обманывает, разберём в [уроке о
метриках](03_metrics.md). Если все ошибки одинаково важны, второй вариант
выглядит предпочтительнее.

Что именно отличает «варианты»? Веса модель подбирает сама на train. Но есть
решения, которые принимает человек до обучения: словарь из слов или из троек
букв, сила ограничения весов, глубина дерева. Такие настройки называют
**гиперпараметрами**, hyperparameters, в отличие от обучаемых параметров. Их и
выбирают по validation.

## Почему validation и test выполняют разные роли

Мы только что использовали validation для решения: выбрали второй вариант.
Теперь можем изменить его настройку, снова проверить и оставить результат
получше. Хотя веса не обучаются напрямую на validation, наши инженерные решения
уже зависят от этой части данных.

Если достаточно долго перебрать варианты, можно найти удачное совпадение с
особенностями именно этих 200 обращений. Например, в них случайно мало опечаток,
и мы выберем модель, которая плохо переносит опечатки в реальном потоке.

Поэтому 200 test-обращений пока не используем. Закончив выбор, запускаем на них
выбранное решение. Получаем проверку на данных, которые не участвовали ни в
обучении, ни в выборе настроек. Test не гарантирует отсутствие будущих проблем,
но устраняет один важный источник завышенной оценки.

Если после просмотра ошибок test мы меняем модель и опять проверяем на нём, эта
часть начинает выполнять роль validation. Это допустимый этап исследования, но
для новой независимой итоговой оценки понадобится другой набор.

## Что именно нужно отделять

В текстовом классификаторе обучаются не только веса. TF-IDF строит словарь и
считает частоты слов. Если сначала вычислить их на всех 1000 обращениях, а затем
разделить данные, преобразование уже использовало будущие проверочные тексты.

Правильный порядок: сначала split — разбиение, затем `fit` преобразования и
модели только на train. На validation и test применяется уже обученное
преобразование. Pipeline помогает соблюдать эту последовательность, но не
исправляет ошибочное разбиение исходных данных автоматически.

Ниже схема работы с уже подготовленными `texts`, `labels` и `model`;
это фрагмент для чтения, а не самостоятельная программа. Полный рабочий
пример обучения находится в `02_examples/01_tickets.py`.

```python
from sklearn.model_selection import train_test_split

# texts, labels — списки из 1000 обращений и их меток.
# Сначала откладываем 200 в test, затем делим остаток 600/200.
x_rest, x_test, y_rest, y_test = train_test_split(
    texts, labels, test_size=200, random_state=42)
x_train, x_val, y_train, y_val = train_test_split(
    x_rest, y_rest, test_size=200, random_state=42)
model.fit(x_train, y_train)      # Pipeline: TF-IDF и модель видят только train
```

`train_test_split` перемешивает строки случайно; `random_state` фиксирует это
перемешивание, чтобы разбиение повторялось при каждом запуске. Случайное
перемешивание подходит не всегда — об этом следующий раздел урока.

## Когда случайное разбиение даёт неверный ответ

Представь, что одно обращение скопировали пять раз с небольшими изменениями.
Если четыре копии попали в train, а пятая — в test, последняя не является
по-настоящему новым случаем. Нужно держать связанные примеры вместе. Аналогично
разделяют по клиентам, если цель — работать с клиентами, которых модель раньше
не видела.

Если мы предсказываем будущие события, обучающие данные должны предшествовать
проверочным по времени. Случайное перемешивание прошлого и будущего может
передать информацию из будущего в обучение. Например, поле «команда, закрывшая
обращение» нельзя использовать, чтобы решить, куда отправить только что
поступившее обращение.

Такое использование недоступной при реальном предсказании информации называют
**утечкой данных**. Она отличается от обычной сложной задачи: эксперимент
проверяет не тот сценарий, в котором система будет работать.

## Как записать результат сравнения

Сохрани состав частей, способ подготовки признаков, настройки моделей и
результаты. Добавь несколько ошибок с объяснением, а не только среднюю долю
совпадений. Так можно понять, исправило ли изменение нужный тип проблем.

В следующем уроке уточним, как измерять качество, если ошибки имеют разную цену.
Затем отдельно разберём кросс-валидацию — способ уменьшить зависимость от одного
разбиения — и регуляризацию — ограничение сложности модели.

2. Веса модели на этой выборке напрямую не обучались. Делает ли это итоговую
   оценку на ней независимой?
3. Почему случайное (не по времени) разбиение может дать слишком оптимистичную
   оценку для задачи предсказания будущих событий?

<details>
<summary>Разбор вопроса 3</summary>

Случайное перемешивание может поместить более поздние по времени примеры в
train, а более ранние — в validation/test, то есть модель косвенно «видит
будущее» относительно момента предсказания. В реальном использовании такой
информации из будущего не будет — train должен предшествовать проверочным данным
по времени, иначе оценка окажется лучше, чем реальная работа системы.

</details>
