# Что делать, если результат зависит от разбиения

Мы научились сравнивать модели на validation. Но представь, что в случайно
выбранную проверочную часть попали почти одни короткие обращения. Модель для
коротких текстов выиграет, хотя на длинных она слабее. В этом уроке разберём
**кросс-валидацию**: несколько обучений и проверок на разных частях доступных
данных.

Сначала прочитай [разделение train/validation/test](02_model_selection.md).
Кросс-валидация не отменяет независимую итоговую проверку.

## Один маленький пример

Пусть для выбора настройки доступны 12 учебных обращений. Отдельный test уже
отложен, эти 12 обращений в него не входят. Разделим их на три группы: A, B и
C по четыре обращения. Такие части называют **folds**, или фолдами.

| Попытка | На чём обучаем новую модель | На чём проверяем |
|---|---|---|
| 1 | B + C | A |
| 2 | A + C | B |
| 3 | A + B | C |

Каждый раз обучение начинается заново. Нельзя продолжить обучение первой
модели на A, а затем считать проверку на B независимой: первая модель уже
видела B. Если есть TF-IDF или другое обучаемое преобразование, его также
строят заново на обучающих группах конкретной попытки.

Допустим, доли правильных ответов равны 0.75, 1.0 и 0.5. Среднее
`(0.75+1+0.5)/3=0.75`. Вместе со средним мы видим заметный разброс: результат
зависит от того, какая группа проверяется.

Теперь для другой настройки повторим **те же разбиения**. Так сравнение будет
меньше зависеть от случайного выбора групп. Сравниваем средние и разброс, а не
выбираем самую удачную отдельную попытку.

## То же в scikit-learn

`cross_val_score` сам делит данные на фолды, для каждой попытки заново обучает
переданную модель и возвращает по числу на фолд. Возьмём 12 обучающих обращений
из `data/tickets.json` — ровно размер нашего примера:

```python
import json
from pathlib import Path

from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import cross_val_score
from sklearn.pipeline import make_pipeline

rows = json.loads(Path('data/tickets.json').read_text())   # запуск из корня
train = [r for r in rows if r['split'] == 'train']
texts = [r['text'] for r in train]
labels = [r['label'] for r in train]

model = make_pipeline(TfidfVectorizer(), LogisticRegression())
scores = cross_val_score(model, texts, labels, cv=3)   # accuracy на 3 фолдах
print(scores, scores.mean().round(3))                  # [0.5 0.  0.5] 0.333
```

Pipeline здесь важен: TF-IDF тоже строится заново на обучающих фолдах каждой
попытки. Результат отрезвляет. В [примере
`01_tickets.py`](../02_examples/README.md) та же модель угадала все 6
test-обращений, а здесь средняя accuracy 0.333 и один фолд с нулём. Каждая
попытка обучается всего на 8 текстах, и слова проверочного фолда почти не
встречались в обучающих. Оба числа описывают крошечный учебный набор: 6 удачных
ответов — не доказательство качества, и разброс по фолдам это показывает.

## Что делать после выбора

Выбрав настройку по кросс-валидации, обычно обучают одну итоговую модель на
всех данных, выделенных для обучения и настройки в этом эксперименте. Затем
один раз применяют её к отложенному test. Состав данных и параметры фиксируют
в отчёте.

Кросс-валидация требует несколько обучений. Если один запуск занимает день,
пять фолдов для десяти вариантов могут оказаться слишком дорогими. Иногда
разумнее использовать одно хорошо спроектированное validation-разбиение и
ограниченный перебор. Метод выбирается с учётом данных, стоимости и цели
проверки.

## Какие строки нельзя разносить по фолдам

Если обращения одного клиента очень похожи и будущая задача касается новых
клиентов, держи клиента целиком в одной группе. В scikit-learn для этого есть
`GroupKFold`: ему передают список групп (например, ID клиента для каждой
строки), и строки одной группы всегда попадают в один фолд. Для будущих событий
используй временной порядок: обучение на более раннем, проверка на более
позднем. Перемешивание времени ради одинакового размера фолдов может нарушить
смысл эксперимента.

**Стратификация** старается сохранить доли классов в частях. Она полезна,
когда редкий класс иначе может полностью исчезнуть из проверки, но не решает
проблему связанных клиентов или времени. Сначала выбирают разбиение по смыслу
задачи, затем учитывают баланс.

## Что означает вложенная кросс-валидация

Это дополнительный уровень той же идеи. Внешнюю часть оставляют для оценки, а
внутри оставшихся данных проводят собственную кросс-валидацию для выбора
настройки. Затем проверяют выбранное решение на внешней части. Так повторяют
для внешних фолдов.

Она нужна, когда хотят оценить саму процедуру выбора модели без использования
внешней части в настройке. На первом проекте можно обойтись понятным
train/dev/test; важнее соблюдать разделение ролей данных, чем механически
добавить сложный метод.

## Проверить понимание

1. Почему нельзя построить TF-IDF по всем данным, а затем проводить
   кросс-валидацию только классификатора?
2. Когда обычной (не вложенной) кросс-валидации для подбора настроек уже
   недостаточно?
3. Accuracy на пяти фолдах: `[0.80, 0.82, 0.79, 0.81, 0.80]` у варианта A и
   `[0.95, 0.60, 0.90, 0.70, 0.85]` у варианта B. Средние почти равны. Что
   ещё говорят эти числа?

<details>
<summary>Разбор вопроса 1</summary>

Словарь и частоты уже использовали тексты проверочной части каждого фолда.
Чтобы проверять весь способ обучения честно, преобразование должно учиться
только на обучающих данных каждой попытки. Поэтому его объединяют с моделью в
Pipeline.

</details>

<details>
<summary>Разбор вопроса 2</summary>

Вложенная кросс-валидация полезна, когда сам ПОДБОР настроек
(например, перебор нескольких значений гиперпараметра) опирается на те же
фолды, по которым затем сообщается итоговое качество — внешний контур честно
оценивает качество, внутренний занимается только выбором настроек, не видя
данные внешней проверки. Без вложенности число, полученное после подбора
лучшей настройки на тех же фолдах, может быть оптимистично смещено.
Альтернатива — независимый test, не участвовавший в выборе настроек.

</details>

<details>
<summary>Разбор вопроса 3</summary>

Средние: A — `4.02/5=0.804`, B — `4.00/5=0.800`. Но у B результат сильно зависит
от того, какие данные попали в проверку: от 0.60 до 0.95. Возможно, B хорошо
решает одну часть обращений и плохо другую — стоит посмотреть, чем отличаются
слабые фолды. При равных средних стабильный вариант A предсказуемее.

</details>
