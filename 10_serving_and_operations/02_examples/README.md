# Примеры и эксперименты

Команды выполняются из корня репозитория после установки зависимостей.
Три примера из четырёх (профиль **CPU**) не требуют весов и сети.
`02_benchmark.py` (профиль **MODEL**) читает только локальные веса:
[где взять модели](../../data/models.md). Пока веса не подготовлены, он
завершается сообщением «Модель отсутствует» — это не успешный запуск.

Различай три вида результата. **Расчёт** — число по формуле (память в
`01_memory.py`). **Симуляция** — учебные данные или учебные часы
(`03_release_gate.py`, `04_trace.py`). **Измерение** — реальное время на
твоём компьютере (`02_benchmark.py`). Только измерение зависит от
оборудования, и только его нельзя переносить на другую машину.

Для каждого опыта сначала запиши предсказание, затем измени одно условие и
сравни.

## 01_memory.py — расчёт памяти весов и KV cache

После урока [Как модель становится сервисом](../01_theory/01_serving_basics.md).
Профиль **CPU**, это расчёт, а не измерение.

```bash
uv run python 10_serving_and_operations/02_examples/01_memory.py
```

Входные данные записаны в коде: три размера модели (135 млн, 1 млрд,
3 млрд параметров) и учебная конфигурация для KV cache — 24 слоя, 1 запрос,
8 KV-голов по 64 числа, 2 байта на число, 2048 и 4096 токенов. Функция
`kv_bytes` — та же формула, что в уроке; её аргументы идут в том же
порядке.

Как читать вывод. Первые три строки — только веса в FP32: для 135 млн
получается `0.503` GiB, как в уроке. Строка `Example KV cache GiB: 0.09375
double context: 0.1875` — KV cache одного запроса: `2×24×1×2048×8×64×2 =
100 663 296` байтов, то есть 0.09375 GiB; при 4096 токенах ровно вдвое
больше. `assert` в конце проверяет это удвоение.

Что доказывает: KV cache растёт линейно с числом токенов, а веса — нет.
Чего не доказывает: сколько памяти реально займёт процесс. В расчёт не
входят библиотеки, активации, служебные данные квантизации.

Одно изменение. Поменяй `8` (число KV-голов) на `32` в обоих вызовах
`kv_bytes`, как если бы модель не использовала GQA и хранила K/V для
каждой query-головы. Предскажи заранее: во сколько раз вырастет кэш?
Ответ — в 4 раза (0.375 GiB для 2048 токенов). Если получилось иначе,
проверь, что изменил оба вызова.

## 02_benchmark.py — измерение полного generate

После урока [Как модель становится сервисом](../01_theory/01_serving_basics.md).
Профиль **MODEL**: нужны веса `artifacts/models/smollm2-135m`.

```bash
uv run python 10_serving_and_operations/02_examples/02_benchmark.py
```

Без весов скрипт сразу останавливается с сообщением «Модель отсутствует.
См. data/models.md». С весами он загружает модель один раз, делает один
прогревочный вызов и три замера `generate()` по 24 новых токена с
жадной генерацией на двух потоках CPU. Результат печатается и
сохраняется в `artifacts/benchmark.json`.

Как читать вывод. `warmup seconds` — первый вызов: он медленнее из-за
выделения памяти и ленивой инициализации, поэтому в замеры не входит.
`seconds` — три полных времени вызова, `output_tokens` — сколько новых
токенов выдано, `output_tokens_per_second` — их отношение. Числа зависят
от процессора и нагрузки на компьютер и меняются от запуска к запуску.

Что доказывает: сколько длится полный вызов на твоей машине при одном
запросе за раз. Чего не доказывает: это не TTFT (первый токен отдельно не
наблюдается) и не скорость под нагрузкой; трёх замеров мало для p95.

Одно изменение. Поменяй `max_new_tokens=24` на `48`. Предскажи: вырастет
ли время вдвое? Prefill (обработка входа) выполняется один раз при любой
длине ответа, поэтому рост может оказаться меньше двукратного. Сверь
`output_tokens`: если модель закончила ответ раньше лимита, токенов будет
меньше 48, и сравнивать надо время на токен.

## 03_release_gate.py — правила выпуска по готовым метрикам

После урока [Как проверить сервис перед
выпуском](../01_theory/03_release_and_drift.md). Профиль **CPU**,
симуляция: метрики не измерены, а заданы в коде.

```bash
uv run python 10_serving_and_operations/02_examples/03_release_gate.py
```

Входные данные — три учебных отчёта о версии: доля верных ответов
`quality`, задержка `p95_ms` и число нарушений доступа `acl_failures`.
Функция `release_gate` сначала проверяет сам отчёт (все три метрики есть,
числа конечные), затем отдельно каждое правило: `quality ≥ 0.85`,
`p95_ms ≤ 1500`, `acl_failures = 0`.

Как читать вывод. Для каждого отчёта печатается `approved` и список
`reasons` — нарушенных правил. Первый отчёт проходит; второй с лучшим
качеством не проходит из-за одной утечки (`authorization`); третий не
проходит сразу по двум причинам.

Что доказывает: критическое ограничение не компенсируется средней
метрикой, а пропущенное измерение (NaN) — ошибка, а не «всё хорошо».
Чего не доказывает: что пороги 0.85 и 1500 мс подходят твоему продукту —
они учебные.

Одно изменение. Добавь `'eval_size'` (размер проверочного набора) в
множество `required` и правило «не меньше 200» в список проверок, но
отчёты пока не меняй. Предскажи, что произойдёт с тремя отчётами. Ответ:
первый же вызовет `ValueError('Incomplete release report')`, потому что
`required` сравнивается с полями отчёта целиком. Добавь поле во все
отчёты и проверь правило на значении 150.

## 04_trace.py — дерево trace одного RAG-запроса

После урока [Как увидеть, что происходит внутри
запроса](../01_theory/04_llm_observability.md). Профиль **CPU**,
симуляция: время учебное.

```bash
uv run python 10_serving_and_operations/02_examples/04_trace.py
```

`span` — контекстный менеджер: `with span(...)` открывает запись об операции и
закрывает её при выходе из блока. Как устроены `with` и
`@contextlib.contextmanager` в общем случае — в [уроке о контекстных
менеджерах](https://github.com/krasnosvar/4_python_my_knowledgebase/blob/main/1_python/2_functions_and_decorators/01_theory/06_context_managers.md).
Функция `work(ms)` не ждёт, а сдвигает учебные часы `clock_ms`, поэтому вывод
одинаков при каждом запуске.

Как читать вывод. Отступ показывает вложенность: `retrieve` — ребёнок
`request`, `embed_query` — ребёнок `retrieve`. Число — длительность span
в миллисекундах, после него — атрибуты. Ключ `sk-abc123` из вопроса
напечатан как `sk-***`: маскирование выполняется до записи. Разбор этого
дерева по шагам — в уроке.

Что доказывает: как вложенные `with` дают дерево и почему здесь, при
последовательных детях, длительность родителя не меньше их суммы. При
параллельных детях сумма может быть больше. Чего не доказывает: как работает
настоящая библиотека трассировки — она берёт время из системных часов и
отправляет spans во внешнее хранилище.

Одно изменение. Внутри `with span('retrieve', ...)` после
`vector_search` добавь:

```python
with span('rerank'):
    work(40)
```

Предскажи заранее: `retrieve` станет 150 мс, `request` — 2945 мс,
`llm.generate` не изменится.
