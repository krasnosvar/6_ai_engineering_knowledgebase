[Код решения](solution.py). Проверка эталона из корня:

```bash
uv run python 9_agents_and_tools/03_exercises/check.py --answers
```

Ожидается `PASS: 9_agents_and_tools answers`.

## 1. `validate_action`

Ход мысли: модель только предлагает действие, исполнитель проверяет его
вне модели и не расширяет права по тексту запроса. Поэтому проверяем
белым списком (allow-list): описываем единственную допустимую форму и
отвергаем всё, что с ней не совпадает. Сравнение `set(action) == {'tool',
'arguments'}` сразу отсекает и недостающие, и лишние поля.

Типичные ошибки: проверять «нет ли запрещённого» вместо «ровно ли
разрешённое» — любое новое поле или инструмент проскочит; проверить
`tool`, но забыть лишние ключи в `arguments` (`{'service': 'demo', 'cmd':
'x'}`); обращаться к `action['tool']` до проверки, что `action` —
словарь, — тогда на списке упадёт `TypeError` вместо `ValueError`.

## 2. `may_continue`

Ход мысли: два независимых условия остановки — бюджет и отмена — и оба
должны разрешать шаг: `steps < limit and not cancelled`. Сравнение
строгое: при `steps == limit` бюджет уже исчерпан. Типы проверяются через
`type(...) is int`, потому что `True` — тоже `int`, и `may_continue(True,
2, False)` иначе прошёл бы как один шаг.

Типичная ошибка: `steps <= limit` — агент сделает на один шаг больше
лимита.

## 3. Timeout изменяющего действия

Timeout означает «исход неизвестен», а не «не выполнено»: запрос мог
дойти, сервис — перезапуститься, а потеряться только ответ. Поэтому
операция переходит в состояние «исход неизвестен», и следующий шаг —
проверить статус по ID операции, а не выполнить её заново. Если статус
узнать нельзя, повтор допустим только с тем же ID и при идемпотентном
исполнителе: тогда журнал вернёт прежний результат. Повтор с новым ID —
новое действие, второй перезапуск. В `03_idempotency.py` журнал живёт в
памяти: после рестарта процесса он пуст, и повтор `op1` выполнится снова;
два одновременных вызова могут оба не найти ID и оба выполнить эффект.
Нужны долговременное хранилище и атомарное резервирование операции.
Если сбой произошёл после внешнего эффекта, но до записи результата,
дополнительно нужна проверка исхода или идемпотентность внешнего сервиса.

## 4. `handle_jsonrpc`

Ход мысли — порядок проверок:

1. Форма запроса. Неверный запрос — ошибка вызывающего кода, поэтому
   `ValueError`, а не ответ: хост не должен отправлять такое серверу.
2. `tools/list` возвращает пересечение того, что умеет сервер, и того,
   что разрешил хост: модель не должна даже узнать о `restart_service`.
   `sorted` делает ответ независимым от порядка ключей словаря.
3. `tools/call`: сначала форма `params`, затем политика хоста, и только
   потом поиск инструмента. Политика раньше поиска — запрещённая функция
   не запускается вовсе; это проверяет список `calls` в `check.py`.
4. Два вида неудачи. `ValueError` внутри инструмента превращается в
   `result` с `isError: True`: модель прочитает текст и может исправить
   аргументы. Неизвестный метод или инструмент — поле `error` с кодом;
   его обрабатывает код хоста.

Прочие исключения инструмента решение не перехватывает: `TypeError` или
`KeyError` внутри функции — ошибка программы, её нужно увидеть, а не
показать модели как обычный ответ.

Типичные ошибки: проверить `name in tools` раньше `name in allowed` —
тогда на выдуманное имя придёт `Unknown tool`, а на `restart_service` —
`Tool not allowed`, и по разнице ответов модель узнает, что запрещённый
инструмент существует; перехватывать `except Exception` и
отдавать модели любую ошибку как `isError`; возвращать в `tools/list` все
инструменты сервера без фильтра хоста.

## 5. `agent_tokens` и `multi_agent_cost`

Ход мысли: на шаге `i` читается `system + per_step × i`, значит за `n`
шагов `system × n + per_step × (0 + 1 + ... + (n − 1))`. Сумма первых
`n − 1` чисел равна `n × (n − 1) / 2` — например, для `n = 6`: `6 × 5 / 2
= 15`, как в уроке. Деление нацело `//` точное, потому что из двух
соседних чисел `n` и `n − 1` одно чётное. Цикл по шагам дал бы тот же
ответ; формула нужна, чтобы видеть, что цена растёт как квадрат числа
шагов.

`multi_agent_cost` складывает исполнителей и два вызова оркестратора:
`3 × 19500 + 2000 + 2900 = 63400`. Сравнение с одним агентом на `6 ×
workers` шагов:

| workers | Один агент | Оркестратор и исполнители | Дешевле |
|---|---|---|---|
| 1 | 19500 | `19500 + 2000 + 2300 = 23800` | один агент |
| 2 | `2000 × 12 + 500 × 66 = 57000` | `39000 + 2000 + 2600 = 43600` | оркестратор |
| 3 | 112500 | 63400 | оркестратор |

Уже с двух независимых областей схема с исполнителями дешевле. Выигрыш
даёт не деление само по себе, а то, что история каждого исполнителя
короче. При одной области исполнитель и оркестратор — чистые накладные
расходы.

Типичные ошибки: считать сумму с `1` до `n` вместо `0` до `n − 1` (на
первом шаге наблюдений ещё нет) — для 6 шагов выйдет 22500 вместо 19500;
забыть один из вызовов оркестратора; проверять типы через `isinstance` и
пропустить `True`.

Эти проверки подтверждают контракт функций на обычных и граничных
случаях. Для освоения темы также нужен письменный ответ на задание 3 и
самостоятельные эксперименты из [примеров](../02_examples/README.md).
