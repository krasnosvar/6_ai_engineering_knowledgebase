# Примеры и эксперименты

Команды выполняются из корня репозитория после установки зависимостей.
Три примера из четырёх (профиль **CPU**) не требуют весов и сети.
`02_model_tool.py` (профиль **MODEL**) читает только локальные веса:
[где взять модели](../../data/models.md). Пока веса не подготовлены, он
завершается сообщением «Модель отсутствует» — это не успешный запуск.

Все CPU-примеры — **симуляции**: «метрики», «перезапуск» и «сервер»
здесь учебные, предложения «модели» заданы в коде заранее. Они проверяют
код вокруг модели — исполнитель, журнал операций, обмен сообщениями, — а
не то, насколько хорошо модель выбирает действия. Выбор действия моделью
показывает только `02_model_tool.py`.

Для каждого опыта сначала запиши предсказание, затем измени одно условие и
сравни.

## 01_executor.py — исполнитель с проверкой и бюджетом шагов

После урока [как модель может пользоваться
инструментами](../01_theory/01_tool_calling.md). Профиль **CPU**,
симуляция.

```bash
uv run python 9_agents_and_tools/02_examples/01_executor.py
```

Входные данные — действия в формате урока, записанные в коде:
`{'tool': 'read_metrics', 'arguments': {'service': 'demo'}}` и
запрещённое `{'tool': 'shell', ...}`. Функция `execute` — исполнитель:
проверяет ровно те поля, имя инструмента и сервис, а при нарушении
поднимает `ValueError`. Функция `run` — цикл агента: выполняет действия по
очереди, пока не кончится список или лимит `max_steps=2`, и возвращает
статус с журналом `trace`. Если `execute` поднял ошибку, `run` перехватывает
её (`try`/`except`) и возвращает статус `rejected` с причиной, а не
падает.

Как читать вывод. Сначала молча проходят три `assert`: одно разрешённое
действие — `completed`; три действия при лимите 2 — `budget_exhausted`;
`shell` — `rejected`. Затем печатается результат одного разрешённого
шага: `status` и `trace`, где `observation` — данные «инструмента» с
пометкой `source: synthetic fixture`, то есть заранее заданные числа.

Что доказывает: исполнитель пропускает только точно разрешённое, а цикл
честно сообщает, почему остановился. Чего не доказывает: что модель
предложит правильное действие, и ничего о реальных метриках.

Одно изменение. Замени последнюю строку `print(run([good]))` на
`print(run([good, {'tool': 'read_metrics', 'arguments': {'service':
'private'}}]))` — второе действие просит чужой сервис. Предскажи статус и длину
`trace`. Должно получиться `rejected` с причиной `Only the demo service is
authorized` и одним шагом в `trace`: первое действие выполнено, второе
отклонено. Отсюда вывод урока: исход цикла — это статус плюс журнал, а не «всё
или ничего».

## 02_model_tool.py — один выбор инструмента маленькой LLM

После урока [как модель может пользоваться
инструментами](../01_theory/01_tool_calling.md). Профиль **MODEL**: нужны
веса `artifacts/models/smollm2-135m`. Сеть во время запуска не нужна.

```bash
uv run python 9_agents_and_tools/02_examples/02_model_tool.py
```

Без весов скрипт сразу останавливается с сообщением «Модель отсутствует.
См. data/models.md». Этот путь проверен запуском; ответ модели в курсе
запуском не проверялся, потому что веса в репозиторий не входят.

Что делает. Инструмент описан словами прямо в тексте запроса (не через
native function calling), модель жадно генерирует до 64 токенов. Строка
`MODEL:` — её ответ как есть. Затем ответ разбирается `json.loads` и
передаётся исполнителю `run` из `01_executor.py` — тому же, что в
CPU-примере. Строка `RESULT:` — честный итог шага: `completed`,
`rejected` с причиной или `invalid_json`, если модель вернула не JSON.

Как читать вывод. Любой из трёх статусов — нормальный результат
эксперимента, а не сбой примера: маленькая модель на 135 млн параметров
часто ошибается в формате. Жадная генерация повторяется при тех же
весах и запросе, но другая версия модели или библиотеки может дать
другой ответ.

Что доказывает: как выглядит граница «модель предлагает — код
проверяет» на настоящем ответе. Чего не доказывает: что модель
надёжно выбирает инструмент — для этого нужен набор задач и доля верных
выборов, как в [разделе 7](../../7_evaluation_and_safety/README.md).

Одно изменение. Перепиши текст запроса в `messages` двумя-тремя
способами (например, убери пример JSON) и запиши статус для каждого.
Предскажи заранее, какая формулировка чаще даст `completed`. Не скрывай
`invalid_json`: это и есть измеряемая ошибка.

## 03_idempotency.py — повтор операции после потерянного ответа

После урока [что делать, если действие выполнено, а ответ
потерялся](../01_theory/02_state_and_retries.md). Профиль **CPU**,
симуляция побочного эффекта: настоящего перезапуска нет, есть счётчик.

```bash
uv run python 9_agents_and_tools/02_examples/03_idempotency.py
```

Входные данные — сценарий урока, записанный в коде. Класс `Sandbox` хранит
журнал `operations` (ID операции → сервис и результат) и счётчик `restarts` —
сколько раз эффект действительно произошёл. Метод `restart` сначала ищет ID в
журнале: если нашёл, возвращает прежний результат без нового эффекта. Синтаксис
классов — урок [что такое
класс](https://github.com/krasnosvar/4_python_my_knowledgebase/blob/main/1_python/3_oop/01_theory/01_what_is_a_class.md)
в Python-базе.

Как читать вывод. Строка `Retries for op1 caused one effect; new op2
caused a second effect.` печатается только после `assert`: два вызова с
`op1` («ответ потерялся, повторили») дали один перезапуск, вызов с `op2`
— второй. Вторая строка напоминает, чего пример не умеет.

Что доказывает: повтор с тем же ключом не повторяет эффект, новый ключ
означает новое действие. Чего не доказывает: защиту при рестарте
процесса (журнал живёт в памяти) и при двух одновременных вызовах
(проверка и запись не атомарны).

Одно изменение. Сейчас разрешён только `demo`, поэтому проверка
`Operation ID reused with different arguments` никогда не срабатывает.
Разреши второй сервис: замени `service != 'demo'` на `service not in
{'demo', 'staging'}` и добавь в конец вызов `s.restart('op1',
'staging')`. Предскажи: выполнится ли перезапуск `staging`? Должен
получиться `ValueError: Operation ID reused with different arguments` —
тот же ключ с другими аргументами отклоняется, как сказано в уроке.

## 04_mcp_toy.py — обмен сообщениями в стиле MCP

После урока [как подключать инструменты через MCP](../01_theory/03_mcp.md).
Профиль **CPU**, учебная имитация без SDK и сети; это не реализация
протокола.

```bash
uv run python 9_agents_and_tools/02_examples/04_mcp_toy.py
```

Входные данные. Один файл играет две роли. Без флага он — хост с
клиентом (`main`): запускает самого себя с флагом `--server` дочерним
процессом через `subprocess.Popen` и общается с ним строками JSON через
его стандартный ввод и вывод — это транспорт stdio из урока. Сервер
(`handle`, `serve`) знает два инструмента, `TOOLS`; хост разрешает один,
`ALLOWED_TOOLS = {'read_metrics'}`. Три предложения «модели» заданы в
`proposals`.

Как читать вывод. `->` — сообщение клиента серверу, `<-` — ответ:

1. `initialize` → имя сервера и `capabilities`;
2. `tools/list` → оба инструмента со схемами `inputSchema`; строка
   `сервер предлагает: [...] | модели показываем: ['read_metrics']` —
   фильтр хоста;
3. `tools/call` для `demo` → `result` с `"isError":false` и метриками;
4. `tools/call` для `billing` → `result` с `"isError":true`: инструмент
   запустился, но не справился, модель может прочитать текст;
5. `хост отклонил без вызова сервера: restart_service` — запрос к
   серверу даже не отправлен.

Что доказывает: форму сообщений и то, что решение о допуске принимает
хост. Чего не доказывает: совместимость с настоящими MCP-клиентами и
серверами, безопасность сервера.

Одно изменение. Добавь `'restart_service'` в `ALLOWED_TOOLS`. Предскажи
две вещи: появится ли инструмент в списке «модели показываем» и что
ответит сервер на вызов. Должно получиться: инструмент показан, а сервер
вернёт `error` с кодом `-32602` и `Unknown tool` — игрушечный сервер
объявил `restart_service` в `tools/list`, но исполнять его не умеет.
Это ошибка протокола, а не `isError`. Затем реши письменно, какое
подтверждение человека нужно было бы перед настоящим перезапуском.
