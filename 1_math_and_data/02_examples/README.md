# Примеры раздела 1

Все три примера — профиль **CPU**: веса моделей и сеть не нужны.
Команды выполняются из корня репозитория после `uv sync --frozen`. Перед
запуском запиши, что ожидаешь увидеть, после — сравни с выводом.

В конце каждого примера стоит `assert` — проверка, что результат совпал
с ожидаемым для исходных настроек. Когда ты меняешь условия опыта, такая
проверка может упасть с `AssertionError`. Это не поломка: напечатанные
до неё строки и есть результат опыта.

## 01_gradient.py — обучение линейной модели

Выполняется после [урока о градиенте](../01_theory/07_gradients.md).
Показывает, что формулы градиента из урока верны и что повторение шага
обучения находит правильные параметры.

```bash
uv run python 1_math_and_data/02_examples/01_gradient.py
```

Данные: пять точек `x = -2, -1, 0, 1, 2`, а `y` посчитаны точно по
формуле `y = 2x + 1`. В уроке было два наблюдения, здесь пять, и
правильные параметры известны заранее (`w = 2`, `b = 1`), поэтому видно,
нашло ли их обучение. Функции `loss` и `gradient` — это формулы MSE и
производных из урока; переменная `learning_rate` — скорость обучения.

Вывод и его смысл:

```text
градиент по w: формула=-8.00000, численно=-8.00000
ошибка 9.000000 -> 0.000000000; w=2.00000, b=1.00000
```

- Первая строка: производная по формуле совпала с численной оценкой из
  раздела «Как проверить собственную формулу» для `w` в этой точке. Это
  полезная проверка, но она не доказывает формулу для всех данных и не
  проверяет производную по `b`.
- Вторая строка: начальная MSE при `w = 0`, `b = 0` равна 9. Проверь
  вручную: `y = -3, -1, 1, 3, 5`, предсказания нулевые, ошибки `0 − y`
  равны `3, 1, -1, -3, -5`; квадраты `9, 1, 1, 9, 25`, среднее
  `45 / 5 = 9`. После 100 шагов ошибка почти нулевая, а
  параметры совпали с `2` и `1`.

Что это показывает: в этом запуске градиентный спуск приблизился к
известным параметрам. Чего не доказывает: что модель хорошо предскажет реальное
время обращений. Здесь данные лежат точно на прямой и шума нет.

Опыт: в функции `main` поменяй `learning_rate = 0.1` на `0.01`, затем на
`0.6`. Сначала предскажи, что случится в каждом случае. При `0.01` за 100
шагов ошибка снизится только примерно до 0.02, а параметры не дойдут до
`2` и `1`: шаг слишком мал. При `0.6` ошибка вырастет до огромных чисел:
каждый шаг перескакивает минимум всё дальше, как в разделе урока «слишком
большой шаг». В обоих случаях завершающий `assert` упадёт.

## 02_probability.py — редкие сбои и ложные тревоги

Выполняется после [урока о
вероятности](../01_theory/09_probability.md). Показывает тот же пример
с детектором сбоев, но не таблицей, а симуляцией: программа сама разыгрывает 100
000 запросов.

```bash
uv run python 1_math_and_data/02_examples/02_probability.py
```

Каждый запрос с вероятностью 1% оказывается сбоем. При сбое тревога
срабатывает с вероятностью 90%, без сбоя — с вероятностью 5%. Генератор
случайных чисел создан с фиксированным начальным значением (`seed`
42), поэтому повторные запуски на той же версии Python дают те же числа.
TP, FP, FN и TN — четыре возможных исхода, они расшифрованы в
комментарии в коде. Precision — доля настоящих сбоев среди тревог,
recall — доля пойманных сбоев.

Вывод на машине, где готовился курс:

```text
{'TP': 865, 'FP': 4895, 'FN': 96, 'TN': 94144}
precision=0.150; recall=0.900
ожидаемая precision по формуле Байеса: 0.154
```

Симуляция дала precision 0.150, а расчёт по формуле из урока — 0.154.
Расхождение — случайность конечного числа запросов, а не ошибка
формулы. Что это доказывает: при редких сбоях большинство тревог
ложные, хотя детектор ловит 90% сбоев. Чего не доказывает: что у
настоящего детектора такие же доли — здесь мы их задали сами.

Опыт: сделай сбои частыми. Поменяй `0.01` на `0.10` в строке
`failure = ...` и в формуле `expected_precision`. Предскажи, вырастет
precision или упадёт. Ожидаемо она вырастет примерно до 0.67: настоящих
сбоев стало в 10 раз больше, а ложных тревог даже немного меньше:
исправных запросов стало меньше. Recall
останется около 0.9. `assert` в конце упадёт: он рассчитан на 1%.

## 03_preprocessing.py — стандартизация только по train

Выполняется после [урока о массивах и
стандартизации](../01_theory/13_standardization.md). Показывает, почему
параметры преобразования данных считают только по обучающей части.

```bash
uv run python 1_math_and_data/02_examples/03_preprocessing.py
```

Данные — те же числа, что в [уроке о
данных](../01_theory/10_uncertainty_and_data.md): train `[1, 2, 3]`
и test `[100, 101]`. Каждая таблица — столбец формы `(число примеров,
1)`, потому что `StandardScaler` из scikit-learn ждёт таблицу «примеры ×
признаки» даже при одном признаке. `fit` вычисляет среднее и
стандартное отклонение, `transform` применяет их к данным, `np.vstack`
ставит таблицы друг под другом.

Вывод:

```text
среднее только по train: [2.] среднее с утечкой: [41.4]
test, преобразованный правильно: [120.0249974  121.24974227]
test, преобразованный с утечкой: [1.21425288 1.23497392]
```

Правильно преобразованный test получил значения около 120: новые данные
на 120 стандартных отклонений дальше от среднего train. Это честный
сигнал, что они не похожи на обучающие. Проверь вручную: отклонение train
`sqrt(((1−2)² + 0 + (3−2)²)/3) ≈ 0.816`, `(100 − 2) / 0.816 ≈ 120`. С
утечкой те же числа стали около 1.2, как будто ничего необычного нет.

Опыт: добавь в train выброс — `[[1.0], [2.0], [3.0], [100.0]]` — и
сравни `StandardScaler` с `RobustScaler` из `sklearn.preprocessing` (он
описан в блоке «Для любопытных» урока о стандартизации). Предскажи, у какого
преобразования обычные точки `1, 2, 3` останутся различимыми. Не обучай
преобразование на test.
