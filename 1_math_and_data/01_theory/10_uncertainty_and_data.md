# Неопределённость оценки и разделение данных

Мы познакомились с [вероятностью](09_probability.md). Теперь разберём,
почему качество на небольшой выборке меняется, и как избежать подсказок
из проверочных данных при подготовке модели.

## Почему качество тоже имеет разброс

Если модель правильно ответила на 8 из 10 вопросов, наблюдаемая точность равна
80%. Возьмём десять других вопросов — число может измениться. Маленький набор
особенно сильно зависит от того, какие задачи в него попали.

Один способ исследовать эту нестабильность — **bootstrap**. Из исходных
результатов многократно выбирают столько же строк **с возвращением**: одна
строка может попасть несколько раз, другая ни разу. Для каждого нового списка
считают метрику. Получается набор возможных оценок, из которого строят
приближённый интервал. В разделе оценки выполним процедуру на числах и сравним
две модели.

Bootstrap не добавляет новых знаний о мире. Если исходные вопросы только
простые, повторное перемешивание не создаст сложных. Сначала нужны данные,
похожие на будущую задачу.

### Мостик к LLM: 82% против 85% — это улучшение?

Промпт (prompt) — текст-инструкция, который отправляют языковой модели;
подробно — в разделе 5. Типичная ситуация: с промптом A чат-бот
правильно ответил на 33 вопроса из 40
(82.5%, «примерно 82%»), с промптом B — на 34 (85%). Разница — ровно один
вопрос. Насколько вообще может колебаться доля на 40 вопросах?

Грубую оценку даёт **стандартная ошибка доли**. Запишем каждый ответ как
1 (верно) или 0 (неверно); тогда доля верных — обычное среднее этих
чисел. Посчитаем разброс таких значений на маленьком примере: ответы
`[1, 1, 1, 0]`, доля `p = 0.75`. Отклонения от среднего `0.25` (три раза)
и `-0.75`, квадраты `0.0625` и `0.5625`, дисперсия `(3×0.0625 + 0.5625)/4
= 0.1875`. Это ровно `p × (1-p) = 0.75 × 0.25`: для значений 0 и 1
дисперсия всегда равна `p×(1-p)`, а стандартное отклонение —
`sqrt(p×(1-p))`.

Нам же важен разброс не одного ответа, а доли по `n` вопросам. Среднее
из `n` независимых результатов с одинаковым распределением колеблется в
`sqrt(n)` раз меньше, чем отдельный результат. Эту связь примем без
вывода; она может не работать при зависимости или неоднородности задач:

```text
SE = sqrt(p × (1 - p) / n)
```

Для промпта A: `0.825 × 0.175 = 0.144`, делим на 40 — `0.0036`, корень
— `0.060`, то есть около 6 процентных пунктов. Для B: `0.85 × 0.15 / 40
≈ 0.0032`, корень `≈ 0.056`. Удобное правило: наблюдаемая доля
примерно в 95% случаев отличается от «настоящей» не больше чем на две
стандартные ошибки. Это приближение, оно хуже работает на очень малых
наборах и долях около 0 или 1. По нему 82.5% на 40 вопросах совместимы с
настоящей точностью примерно от 70% до 95% (`82.5 ± 2×6`).

Разница между промптами — 2.5 пункта, меньше половины стандартной
ошибки. Это в пределах шума: по этим данным нельзя утверждать, что B
лучше. Чтобы стандартная ошибка одной доли сжалась до 1.5 пункта при
той же оценке `p`, нужно `n ≈ 0.85×0.15/0.015² ≈ 570` вопросов. Это
не гарантирует обнаружения разницы в 3 пункта: сравнение двух версий
учитывает разброс их разности и ответы на одних и тех же вопросах.

```python
import math

n = 40
for correct in (33, 34):
    p = correct / n
    se = math.sqrt(p * (1 - p) / n)
    print(correct, p, round(se, 3))   # 33 0.825 0.06 / 34 0.85 0.056
```

Это грубая оценка: она считает вопросы независимыми и не использует то,
что обе версии отвечали на одни и те же вопросы. Честное сравнение
парами, через bootstrap, разобрано в [разделе 7, сравнение
версий](../../7_evaluation_and_safety/01_theory/02_comparing_versions.md).

## Подготовка данных начинается с их смысла

Для каждого примера выясни, откуда он взят, что означает ответ и можно ли
использовать эти данные. Проверь пустые тексты, неверные категории и дубли.
Две копии одного обращения не являются двумя независимыми подтверждениями
качества.

Также отделяй данные, на которых учатся, от данных проверки. Обычно набор
делят на три части:

- **train** (обучающая часть) — по ней подбирают параметры модели;
- **validation**, или dev (настроечная часть), — по ней выбирают
  настройки, например learning rate или вариант модели;
- **test** (проверочная часть) — её открывают один раз в конце, чтобы
  оценить модель на действительно новых данных.

Зачем нужны три части, а не две, подробно разберём на классификаторе
обращений в [разделе 2](../../2_classical_ml/01_theory/02_model_selection.md).
Пока мы оцениваем варианты на validation, числа, которые подбираются по
данным, берут только из train. Даже среднее для преобразования признаков
нужно вычислять по обучающей части. Если обучающие
значения `[1,2,3]`, их среднее 2. Добавление проверочных `[100,101]` даёт 41.4
и меняет само преобразование. Мы использовали информацию, которой не было в
обучающей части. Как именно приводить признаки к одному масштабу по
обучающим данным — стандартизация — разберём в [отдельном
уроке](13_standardization.md).

Когда выбор настроек завершён, модель и преобразования иногда заново
обучают на объединении train и validation. Тогда validation уже нельзя
использовать как независимую оценку; для неё остаётся нетронутый test.

## Проверить понимание

1. Почему bootstrap на десяти только простых вопросах не покажет, как модель
   справится со сложными?
2. Почему при выборе модели по validation нельзя посчитать среднее для
   нормализации признаков по train+validation вместе?
3. Промпт B дал 85% на 40 вопросах. Сколько вопросов нужно, чтобы
   стандартная ошибка стала вдвое меньше, и почему не вдвое больше?

<details>
<summary>Разбор вопроса 1</summary>

Bootstrap многократно пересэмплирует УЖЕ ИМЕЮЩИЕСЯ строки данных с
возвращением — он оценивает, насколько нестабильна метрика на данных ИМЕННО
ТАКОГО состава, но не может создать информацию о сложных вопросах, которых в
исходном наборе попросту нет. Если исходные вопросы только простые, любое
число пересэмплирований даст оценки только по простым вопросам.

</details>

<details>
<summary>Разбор вопроса 2</summary>

Если среднее для нормализации считать по train+validation вместе, параметры
преобразования признаков неявно «подсмотрели» статистику validation-данных ещё
до обучения модели — validation перестаёт быть независимой проверкой, потому
что сам процесс подготовки данных уже использовал информацию из неё. Среднее и
другие параметры предобработки нужно вычислять ТОЛЬКО по обучающей части и
затем применять то же самое преобразование к validation.

</details>

<details>
<summary>Разбор вопроса 3</summary>

160 вопросов, вчетверо больше. В формуле `SE = sqrt(p×(1-p)/n)` число
вопросов стоит под корнем: чтобы корень уменьшился вдвое, подкоренное
выражение должно уменьшиться вчетверо. Проверка: `sqrt(0.85×0.15/160) ≈
0.028` — примерно половина от 0.056. Поэтому точные сравнения близких
версий требуют сотен вопросов, а не десятков.

</details>
