# Разбор: срезы качества, источники, судья и вызов инструмента

[Код решения](solution.py) с комментариями. Проверка эталона из корня:

```bash
uv run python 7_evaluation_and_safety/03_exercises/check.py --answers
```

Проверки подтверждают контракт функций на обычных и граничных случаях.
Для освоения темы нужны и письменные ответы: рубрика и опыт с интервалом.

## 1. `slice_accuracy`

Ход мысли: большой обычный срез может скрыть провал редких случаев,
поэтому считаем долю отдельно по каждому срезу. Нужны два счётчика на
срез — сколько строк и сколько верных; доля — их частное.

Типичные ошибки: делить на общее число строк вместо размера среза;
принять `1` или `'yes'` как успех — `True + 0 == 1`, поэтому без точной
проверки типа число 1 молча посчиталось бы верным ответом.

## 2. `citations_allowed`

Ход мысли: «каждый процитированный ID есть в контексте» — это проверка
подмножества `set(cited) <= set(context)`. Пустое множество — подмножество
любого, поэтому ответ без цитат проходит; требовать цитаты — отдельное
правило.

Типичная ошибка — считать эту проверку доказательством обоснованности.
Она защищает от выдуманных ID, но не от ссылки на документ, который не
подтверждает утверждение.

## 3. Рубрика

Рубрика должна разделять существование источника, поддержку утверждения и
полноту ответа. Пример критериев: каждый ID был в контексте; каждое число
и вывод есть в процитированном фрагменте; ответ содержит запрошенное
значение с единицей; при отсутствии данных ответ отказывается. Два
контрпримера к `citations_allowed`: «бюджет 100 минут [d9]» (неверное
число) и «бюджет 43 минуты, его согласовал CTO [d9]» (второе утверждение
источник не содержит).

## 4. `position_bias_check`

Ход мысли: в первом порядке первым показан A, поэтому победы первого —
`verdicts_ab.count('A')`; во втором первым показан B —
`verdicts_ba.count('B')`. На данных урока это `7 + 7 = 14` из 20 и 6
согласованных пар. Если `first_wins` заметно больше `n`, это сигнал
возможного позиционного смещения: нужны повторы, чтобы отделить его от
случайности. Здесь несогласованные пары считают ничьей по договорённости.

Типичная ошибка — считать в обоих списках победы `'A'`: во втором порядке
A показан вторым, и это уже не «победа первого».

## 5. `judge_calibration`

Ход мысли: три числа из уроков 3 и 4. `p_o` — доля совпадений, `p_e` —
сумма произведений долей одинаковых меток, kappa
`= (p_o − p_e)/(1 − p_e)`. На данных урока: `p_o = 0.75`, `p_e = 0.5`,
kappa 0.5 и 4 ложных одобрения из 10 плохих. Kappa описывает согласие в
целом, а `false_approvals` — ошибку в опасную сторону. Если обе стороны
всегда ставят одну метку, `p_e = 1`, и формула делит ноль на ноль —
функция сообщает об этом `ValueError`, а не возвращает выдуманное число.

Типичные ошибки: считать `p_e` только по метке 1 и забыть слагаемое для
0; принять `True` как метку; вернуть `0` или `nan` при `p_e = 1`.

## 6. `guard_tool_call`

Ход мысли: это слои allow-list и подтверждения человеком в коде. Решение
не зависит от текста запроса и найденных документов, поэтому injection не
может его изменить: неизвестный инструмент запрещён по умолчанию,
`'Search'` не превращается в `'search'`. Противоречивая настройка
(инструмент требует подтверждения, но не разрешён) — ошибка, которую лучше
увидеть сразу, чем получить тихое разрешение.

Типичные ошибки: проверять подтверждение раньше allow-list; приводить имя
к нижнему регистру «для удобства» — это расширяет список разрешённого без
решения человека; возвращать `'allow'` при отсутствии ключа `tool`.

## Дополнительный опыт

На 20 вопросах интервал обычно всё ещё широкий: разница в 1–2 вопроса
редко исключает ноль. Новые независимые вопросы обычно помогают уменьшить
неопределённость, но конкретный интервал может и расшириться. Копии старых
только создают видимость новых данных (урок 2, «Типичная ошибка»).
